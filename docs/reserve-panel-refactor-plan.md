# 备牌面板重构详细计划

> 适用分支：`feature/library-and-deckbuilding-table`  
> 适用阶段：覆盖式备牌面板可用性重构  
> 项目原则：弱规则、弱状态、强同步、强可见性控制。  
> 本计划仅重构覆盖式备牌面板及其选择、确认、归位流程；现有备牌托盘保持当前结构和尺寸不变。

## 1. 背景与问题

当前项目已经放弃超大连续桌布，恢复为 `1800 × 1200` 主桌，并使用一个覆盖主桌的大型抽屉式备牌面板：

```text
reserve-prep-drawer
x = 150
y = 40
width = 1500
height = 1100
display = false
layer = 100
```

该方向符合实际使用需求：

- 对局时主桌保持完整；
- 备牌时打开覆盖式面板；
- 面板关闭后不占用主桌空间；
- 不依赖超大 Board、长距离平移或第二张物理桌面。

当前真正的问题不是抽屉尺寸不足，而是牌库展示方式错误。现有实现把大量卡牌放入几个单行 Holder，并使用接近完整牌宽的横向偏移。资源中实际包含：

| 类型 | 实际数量 | 初始职责 |
| --- | ---: | --- |
| 固定游戏主牌 | 160 | 直接位于摸牌堆，不经过备牌面板 |
| 附加牌 | 31 | 由备牌面板选择后进入备牌托盘扩展槽 |
| 武将牌 | 315 | 由备牌面板决定本局允许或 Ban |
| 身份牌 | 10 | 备牌托盘自带，不经过备牌面板选择 |
| 血量牌 | 项目生成数量 | 备牌托盘自带，不经过备牌面板选择 |

当前把约 290 张扩展武将放入同一横排，必然产生数万像素长度，导致：

- 卡牌大规模溢出抽屉面板；
- 右侧卡牌越过 Board，无法点击或拖取；
- 多层卡牌遮挡主桌与其他面板；
- 用户难以确认哪些牌已选择、哪些牌被遗漏；
- 浏览、拖动、选择和编组混在同一动作中；
- 当前面板几乎无法用于 315 张武将的实际备牌。

因此需要把面板从“若干超长横向牌列”重构为：

> **主分类切换＋二级分类导航＋多行手牌式部分重叠牌带＋批量选择＋确认后统一导入现有备牌托盘。**

## 2. 已冻结的产品边界

### 2.1 保留覆盖式抽屉

继续使用单桌加覆盖式抽屉，不恢复超大连续桌布，不建立左右双桌，也不修改 VirtualTabletop 核心。

### 2.2 备牌托盘保持现状

现有备牌托盘保持：

```text
位置：主桌左下方
尺寸：520 × 220
槽位：武将／身份／扩展／血量
能力：移动、显示／隐藏、布局锁定、自动整理
```

本计划不新增托盘页签，不扩大托盘，不拆分附加牌槽，也不改变其视觉布局。

### 2.3 固定游戏主牌不进入备牌面板

固定游戏主牌，即当前固定基础摸牌堆，继续直接位于主桌 `draw-pile`：

- 不在备牌面板中展示；
- 不要求玩家选择；
- 不进入备牌托盘；
- 不与附加牌概念混合；
- 常规回收和洗牌仅处理摸牌堆及回收区。

### 2.4 备牌面板仅管理两类内容

```text
备牌面板
├── 武将牌：315 张
└── 附加牌：当前资源 31 张
```

不再把附加牌拆成“附加一类／附加二类”。界面只显示一个主分类“附加牌”，但内部允许使用二级分类帮助浏览和一键选取。

### 2.5 身份牌和血量牌由托盘自带

- 身份牌初始进入 `identity-reserve`；
- 血量牌初始进入 `marker-reserve`；
- 两者不在备牌面板中展示和选择；
- 具体身份数量与规则由玩家人工决定；
- 不自动按人数验证身份构成。

## 3. 核心交互流程

```text
打开备牌面板
→ 选择主分类：武将牌／附加牌
→ 选择二级分类
→ 浏览部分重叠牌带
→ 单张切换状态或对当前分类一键操作
→ 查看本局摘要
→ 确认备牌
→ 系统统一将允许武将和选中附加牌盖回并移入现有备牌托盘
→ 锁定并收起备牌面板
```

浏览阶段不再要求玩家把实体牌逐张拖到托盘。

## 4. 面板总体布局

保留 `1500 × 1100` 根抽屉，内部建议划分为：

```text
┌──────────────────────────────────────────────────────────────┐
│ 📦 全套备牌面板     [武将牌] [附加牌]            [收起面板] │
├──────────────┬──────────────────────────────┬────────────────┤
│ 二级分类导航  │ 多行部分重叠牌带浏览区         │ 本局选择摘要    │
│              │                              │                │
│ 全部／标准等  │ 分类标题＋数量＋批量按钮         │ 总数／允许／Ban │
│              │ [卡][卡][卡]……               │ 已选附加牌数量   │
│              │ [卡][卡][卡]……               │ 当前状态         │
│              │ [卡][卡][卡]……               │ 最近变更         │
├──────────────┴──────────────────────────────┴────────────────┤
│ 当前页／当前类批量操作       上一页  1/2  下一页              │
│ 恢复默认｜取消修改｜确认备牌                                  │
└──────────────────────────────────────────────────────────────┘
```

推荐空间比例：

```text
顶部工具栏：约 55 px
左侧二级分类栏：约 190–220 px
中间浏览区：约 950–1000 px
右侧摘要区：约 240–280 px
底部操作栏：约 65–80 px
```

所有子区域必须处于抽屉根节点内部，并使用相对坐标。

## 5. 主分类

顶部只设置两个主分类：

```text
武将牌
附加牌
```

切换主分类时：

- 只显示当前主分类的二级分类导航、牌带和摘要；
- 不移动实体牌；
- 不清除已做出的选择；
- 不复制卡牌；
- 另一主分类的页面整体 `display: false`。

## 6. 二级分类设计

### 6.1 武将二级分类

武将共 315 张，二级分类应来自实际资源元数据，不得再依赖“序号前 25 张为标准、其余全部为扩展”的临时规则。

候选分类结构：

```text
全部武将
标准
风
火
林
山
一将成名
SP
其他
待分类
```

最终分类名称与归属必须以实际资源审计结果为准。无法确认的牌进入“待分类”，不得根据图片风格或序号强行猜测。

### 6.2 附加牌二级分类

附加牌对用户只表现为一个主分类，但内部可按实际用途或来源提供二级分类，例如：

```text
全部附加牌
装备类
锦囊类
模式或特殊牌
其他
待分类
```

分类名不得从当前面板中的 AI 占位文字推断，必须依据实际卡面、来源清单或人工确认结果生成。

### 6.3 二级分类的一键操作

每个二级分类应直接显示数量和批量操作。

武将示例：

```text
标准：25/25 允许
[全部允许] [全部 Ban] [反选]
```

附加牌示例：

```text
装备类：8/12 已选
[全部选取] [全部取消] [反选]
```

批量按钮必须明确作用范围：

- 当前页；
- 当前二级分类；
- 当前主分类。

不得使用含糊的单一“全部选取”按钮。

## 7. 手牌式部分重叠牌带

### 7.1 基本原则

采用与手牌区相似的横向部分重叠视觉，但不直接复用私密手牌 Holder。

备牌牌带不需要：

- `childrenPerOwner`；
- Seat 可见性；
- 手牌翻面 Routine；
- 私密状态；
- 手牌计数逻辑。

只复用以下布局语义：

```text
alignChildren = true
preventPiles = true
stackOffsetX = 约 54–62
stackOffsetY = 0
```

### 7.2 不允许一条牌带容纳全部牌

315 张武将即使按 54 px 步进，也不能放在单一横排中。因此每个二级分类必须被拆成若干短牌带。

建议参数：

```text
卡牌尺寸：90 × 126
水平步进：56–60 px
单条牌带容量：15–17 张
每页牌带数量：4–5 条
每页容量：约 64–80 张
```

以中间浏览区约 980 px 为例：

```text
90 + 16 × 56 = 986 px
```

因此单行最多约 17 张，且最后一张完整露出。

### 7.3 分页

当当前二级分类超过一页容量时，使用分页：

```text
当前分类
├── 第 1 页：最多 4–5 条牌带
├── 第 2 页
└── ……
```

翻页时：

- 当前页 `display: true`；
- 其他页 `display: false`；
- 不移动卡牌；
- 不重新创建卡牌；
- 不改变选择状态。

“全部武将”视图可用于全局摘要和批量操作，但不应再创建第二套 315 张实体牌。全部浏览时只复用同一套页面分组，或按统一分页顺序显示真实卡牌。

### 7.4 溢出保护

浏览视口应增加 `overflow: hidden` 作为最后保护：

- 正常访问依赖分类和分页；
- `overflow: hidden` 只负责阻止异常元素穿出面板；
- 不能把裁切当作访问牌库的主要方式。

### 7.5 卡牌操作

面板中的卡牌应：

```text
movable = false
clickable = true
enlarge = 保留当前原生放大
```

禁止在选择阶段直接拖走卡牌，避免：

- 点击误变为拖动；
- 中间卡牌被抽出导致牌带重排；
- 取消选择时难以归位；
- 多人同时拖牌造成状态冲突；
- 页面出现空洞并失去选择依据。

## 8. 选择状态

### 8.1 武将牌

武将默认策略：

```text
默认全部允许
点击单张 → Ban
再次点击 → 恢复允许
```

状态：

```ts
reserveSelection: 'allowed' | 'banned'
```

视觉要求：

允许：

- 正常亮度；
- 金色或绿色细边框；
- 顶部露出区域显示小型 `✓`。

Ban：

- 牌面降低亮度；
- 红色斜纹或半透明遮罩；
- 顶部露出区域显示 `✕ BAN`；
- 仍可悬停放大查看原牌面。

状态标识必须位于牌带中不会被下一张牌完全遮挡的顶部或左侧露出区域。

### 8.2 附加牌

附加牌统一为一个主分类，默认策略建议：

```text
默认不选取
点击单张 → 选取
再次点击 → 取消
```

状态：

```ts
reserveSelection: 'selected' | 'unselected'
```

默认策略应集中在配置中，后续可以改为“默认全选、只取消少数”，但不得把策略散落在 Widget 生成逻辑中。

视觉要求：

选中：

- 正常亮度；
- 蓝绿或金色边框；
- 顶部显示 `✓ 已选`。

未选：

- 轻微降低亮度；
- 灰色边框；
- 不使用强烈 Ban 标记，避免与武将禁用混淆。

## 9. 本局选择摘要

右侧摘要区只显示状态和清单，不放置实体牌副本。

建议内容：

```text
本局备牌：草稿

武将
总数：315
允许：302
Ban：13

附加牌
总数：31
已选：18
未选：13

最近变更
武将甲：Ban
武将乙：恢复允许
附加牌丙：已选
```

摘要数据必须根据实际 AssetCatalog 生成，不得硬编码 `25 张`、`52 张` 等旧占位文字。

可提供“查看完整 Ban 清单”和“查看完整已选附加牌清单”的本地 `INPUT`，但不得在桌面复制整套卡牌。

## 10. 草稿、确认与部署状态

面板使用轻量状态机：

```ts
reservePanelState: 'draft' | 'confirmed' | 'deployed'
```

### 10.1 draft

- 面板可编辑；
- 卡牌不可拖动；
- 单张与批量选择可用；
- 真实武将和附加牌仍位于面板牌带；
- 托盘武将槽和扩展槽尚未装载本局牌池。

### 10.2 confirmed

点击“确认备牌”后：

1. 显示确认弹窗；
2. 显示实际数量；
3. 保存本局牌单；
4. 将允许的武将统一恢复背面；
5. 将允许武将移动到现有 `general-reserve`；
6. 将选中的附加牌统一恢复背面；
7. 将选中附加牌移动到现有 `extra-reserve`；
8. Ban 武将和未选附加牌继续留在面板；
9. 面板进入只读状态；
10. 自动收起覆盖式抽屉。

此阶段不修改：

- 固定 `draw-pile`；
- `identity-reserve`；
- `marker-reserve`；
- 备牌托盘尺寸、位置和槽位。

### 10.3 deployed

当托盘中的本局牌已经被玩家用于正式对局后，状态可标记为 `deployed`。

本项目不自动发武将、不自动分身份、不判断人数规则；`deployed` 只表示已经进入正常对局流程，防止无条件撤销确认。

## 11. 本局牌单

增加轻量清单，不引入规则引擎：

```ts
interface ReserveManifest {
  state: 'draft' | 'confirmed' | 'deployed';
  allowedGeneralIds: string[];
  bannedGeneralIds: string[];
  selectedExtraIds: string[];
  unselectedExtraIds: string[];
}
```

用途：

- 实时统计；
- 批量操作；
- 防止重复导入；
- 确认弹窗；
- 重开面板时恢复状态；
- 重置与归位；
- 自动测试卡牌唯一性。

Manifest 不记录技能、阵营平衡、人数合法性或任何三国杀规则判断。

## 12. 卡牌来源与归位元数据

每张面板卡牌至少保存：

```ts
libraryType: 'general' | 'extra'
secondaryCategory: string
homePage: string
homeRow: string
homeOrder: number
reserveSelection: string
reserveState: 'library' | 'staged' | 'deployed'
```

归位时必须根据 `homeRow` 与 `homeOrder` 返回正确牌带，而不是全部召回到一个超长 Holder。

不得克隆实体牌。每张牌在任意时刻只存在一份。

## 13. 资源分类与界面文字

### 13.1 实际数量优先

所有界面数量由构建时资源目录生成：

```text
武将：catalog.assets.filter(category === 'generals').length
附加牌：catalog.assets.filter(category === 'gameplay-extra').length
```

不得在界面或 Routine 中硬编码：

- 标准武将 25 张；
- 扩展牌 52 张；
- 任意 AI 推测的扩展名称或数量。

### 13.2 分类审计

实现选择界面前，先建立武将和附加牌二级分类清单。

来源优先级：

1. 原始 manifest 和文件路径；
2. 已有 Card ID、序号和标签；
3. 用户确认的分类映射；
4. 无法确认时进入“待分类”。

不得通过图片颜色或模型猜测扩展包。

### 13.3 界面标题自动生成

示例：

```text
武将牌｜315 张
当前分类：SP｜42 张｜允许 39｜Ban 3
附加牌｜31 张｜已选 18
```

所有标题与计数由实际数据派生。

## 14. 与现有备牌托盘的协调

托盘保持当前四槽：

```text
general-reserve   武将
identity-reserve  身份
extra-reserve     扩展
marker-reserve    血量
```

确认备牌时只写入：

```text
允许武将 → general-reserve
选中附加牌 → extra-reserve
```

托盘自带：

```text
身份牌 → identity-reserve
血量牌 → marker-reserve
```

固定主牌继续位于：

```text
draw-pile
```

常规“收拢洗牌”不得收集备牌面板中的 Ban 或未选牌，也不得自动把托盘内容并入摸牌堆。

## 15. 撤销确认与重置

### 15.1 取消草稿修改

在 `draft` 状态下：

- 恢复进入面板时的选择快照；
- 不移动卡牌；
- 不影响托盘和主桌。

### 15.2 恢复默认选择

- 武将恢复“全部允许”；
- 附加牌恢复项目配置的默认状态；
- 只影响当前草稿；
- 不立即移动实体牌。

### 15.3 撤销确认

只在以下条件全部满足时允许：

- 状态仍为 `confirmed`；
- 所有已确认武将仍完整位于 `general-reserve`；
- 所有已确认附加牌仍完整位于 `extra-reserve`；
- 没有牌进入玩家区域、摸牌堆、回收区或公共桌面。

撤销时：

1. 从托盘召回本轮武将和附加牌；
2. 根据 `homeRow` 与 `homeOrder` 归位；
3. 恢复正面；
4. 恢复 `draft`；
5. 保留此前选择状态供继续修改。

一旦牌已经用于对局，不提供静默撤销，应使用明确的完整重置流程。

### 15.4 完整重置

完整重置必须二次确认，并确保：

- 固定主牌回到摸牌堆；
- 身份与血量回到托盘原槽；
- 武将和附加牌回到各自面板牌带；
- 面板恢复默认选择；
- 不丢失、不复制卡牌；
- Seat 是否清空仍由独立操作决定。

## 16. 权限与同步

建议首版默认由玩家 1／房主管理备牌面板。

其他玩家：

- 可以查看公开卡牌；
- 可以悬停放大；
- 可以查看选择状态与摘要；
- 不修改选择。

可选后续模式：共同编组。

确认、撤销确认和完整重置仍仅由房主执行。

所有选择状态和批量操作属于共享游戏状态，必须在多个浏览器会话中同步。镜头、原生放大和本地 `INPUT` 不强制同步。

## 17. 代码结构建议

### 17.1 新增或重构

```text
src/
├── data/
```

## 21. 验收标准

重构完成时必须满足：

- 使用固定 `1800 × 1200` 主桌和覆盖式抽屉；
- 不恢复超大连续桌布；
- 现有备牌托盘尺寸、位置逻辑和四槽结构不变；
- 固定游戏主牌始终直接位于摸牌堆；
- 备牌面板只管理武将和附加牌；
- 315 张武将全部可以通过分类、牌带和分页访问；
- 任何卡牌都不横向溢出抽屉或 Board；
- 牌带采用可点击的部分重叠布局；
- 面板内卡牌不可拖动但可以原生放大；
- 武将支持单张 Ban 和分类一键允许／Ban；
- 附加牌支持单张选取和分类一键选取／取消；
- 所有数量与类别来自实际资源，不依赖 AI 占位文字；
- 确认后允许武将进入现有武将槽；
- 确认后选中附加牌进入现有扩展槽；
- 身份和血量由托盘自带；
- Ban 和未选牌留在面板；
- 卡牌不会重复、丢失或错误归位；
- 主桌常规洗牌不影响面板牌与托盘备牌；
- 房主和普通玩家权限清楚；
- 至少通过房主、普通玩家和观察者三个会话完成同步验收。

## 22. 非目标

本计划不包含：

- 自动判断武将平衡；
- 自动推荐 Ban 牌；
- 自动判断附加牌是否符合模式；
- 自动决定身份数量；
- 自动发武将或身份；
- 自动合并附加牌到摸牌堆；
- 技能、距离、伤害、回合和胜负判定；
- 修改 VirtualTabletop 客户端；
- 无限桌布或第二张物理桌面；
- 改造现有备牌托盘视觉与槽位。

本次重构的唯一核心目标是：

> **让 315 张武将和全部附加牌在现有覆盖式抽屉中可浏览、可放大、可分类、可批量选择、可确认导入，并彻底消除超长横排造成的溢出和不可操作问题。**

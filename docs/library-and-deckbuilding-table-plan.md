# 牌库与编组桌开发计划

> 适用分支：`refactor/native-vtt-4p-prototype`  
> 项目原则：弱规则、弱状态、强同步、强可见性控制。  
> 本计划描述与主游戏桌共存的第二个功能区域，用于浏览牌库、选择本局牌张、构成牌堆并送入主桌。

## 1. 背景与目标

当前主桌边缘的备牌托盘只适合存放少量备用牌或若干完整牌堆。当武将牌、身份牌和扩展牌数量增加后，所有牌叠放在托盘中会导致：

- 无法快速浏览武将正面；
- 难以按扩展包或其他元数据分类；
- 不便比较和选择本轮使用的武将；
- 身份牌构成不容易人工核对；
- 把选中牌重新收拢、盖回、洗牌并送入主桌的流程繁琐；
- 大量准备阶段组件挤占主游戏桌。

因此新增 **牌库与编组桌区域**，承担：

```text
浏览牌库
→ 选择本局候选牌
→ 排除或暂存牌
→ 核对本局构成
→ 收拢、盖回和洗牌
→ 送入主游戏桌
```

牌库桌不执行三国杀规则判断，也不根据人数自动决定武将数量、身份构成或扩展包组合。

## 2. 核心架构：同房间、同画布、双桌并排

### 2.1 方案变更

原计划采用“主桌／牌库桌互斥显示”。现调整为：

> 在同一个 `.vtt` 房间和同一块超大有限桌布上，将主游戏桌与牌库编组桌左右并排放置。

两张桌共用同一个游戏状态和同一批真实卡牌对象，但占据不同空间区域。每位玩家可以独立缩放和平移自己的视图，因此一名玩家留在主桌时，另一名玩家可以查看牌库桌，不需要全体同步切换页面。

```text
同一块连续桌布
├── 左侧：主游戏桌
├── 中间：过渡与方向提示区
└── 右侧：牌库与编组桌
```

该方案是“实用上接近无限”的超大有限桌面，不追求真正无限坐标，不修改 VirtualTabletop 核心源码。

### 2.2 初始 Board 尺寸

首版建议：

```json
{
  "_meta": {
    "gameSettings": {
      "boardSize": {
        "width": 3600,
        "height": 1400
      }
    }
  }
}
```

尺寸不是最终常量，人工验收允许在以下范围微调：

```text
宽度：3200–4200
高度：1300–1800
```

默认不得直接使用 `10000 × 10000`。过大的 Board 会导致初始视图中过度缩小、导航困难、移动端操作恶化和卡牌遗失风险增加。一般不建议超过约 `5000 × 2500`。

### 2.3 推荐空间划分

以 `3600 × 1400` 为基准：

```text
安全外边距：约 60–80 px
主游戏桌：x=80–1760，y=80–1320
过渡走廊：x=1760–1900
牌库桌：x=1900–3520，y=80–1320
```

具体坐标可由布局生成器统一管理，不允许在多个文件中散落硬编码。

过渡走廊中不放牌堆和玩家模块，只放低干扰方向提示，例如：

```text
← 主游戏桌    牌库与编组桌 →
```

### 2.4 同时存在与独立视图

- 两张桌默认同时存在于同一 Board。
- 不因某个玩家进入牌库区而隐藏其他玩家正在使用的主桌。
- 缩放和平移是当前客户端的视图行为，不改变共享卡牌坐标。
- 玩家之间不强制同步镜头位置。
- 牌堆可以通过明确的“送入主桌”操作跨区移动，不要求玩家长距离手拖整叠牌。
- 已开始对局后，房主可锁定牌库桌的编辑操作，但仍可允许查看。

### 2.5 降级模式

移动端、低分辨率或性能不足时，可以提供“隐藏牌库桌装饰与浏览网格”的降级选项，但：

- 该选项不是默认架构；
- 不能删除或复制卡牌；
- 不能改变主桌状态；
- 隐藏只影响显示，不影响牌库对象和编组状态；
- 重新显示后必须恢复原位置和状态。

## 3. 连续桌布与视觉分区

### 3.1 视觉上接近无限

整块 Board 使用可无缝重复的低干扰毛毡、木纹或暗色纹理：

- 背景覆盖完整 Board；
- 不绘制明显的最外层厚边框；
- 不使用会暴露画布终点的强烈装饰；
- 背景纹理不得影响卡牌识别；
- Board 边缘可以使用非常淡的安全警示带，防止卡牌被拖到极端边缘。

### 3.2 两张桌的识别

主桌与牌库桌使用同一整体风格，但通过不同的轻量桌垫区分：

- 主游戏桌：深绿或木质主桌垫；
- 牌库桌：略偏蓝绿、灰绿或铜色的编组桌垫；
- 两者都使用半透明、低饱和底板；
- 不使用大面积纯白色区域；
- 各桌顶部保留清楚的大标题；
- 标题和区域名必须在缩放后仍可辨认。

### 3.3 导航与防迷失

必须增加：

- 主桌和牌库桌的大标题；
- 中间过渡走廊方向提示；
- 两张桌协调但明显不同的桌垫；
- 可选的小型桌面示意图或区域图例；
- 明确的“送入主桌”“返回牌库”按钮；
- 卡牌来源元数据和归位机制；
- 极端边缘的低调警示区。

若纯 `.vtt` 无法通过 Routine 控制当前客户端镜头，则不得伪造“跳转镜头”功能。此时依赖用户原生缩放和平移，并通过标题、方向标识和分区设计保证可导航性。

## 4. 牌库桌总体布局

推荐结构：

```text
┌────────────────────────────────────────────────────────┐
│ 武将库｜身份库｜游戏牌库｜扩展管理｜锁定｜重置编组桌     │
├────────────┬──────────────────────┬────────────────────┤
│ 分类／扩展栏 │ 牌库浏览与分页展示区   │ 本局候选区           │
│            │                      │                    │
├────────────┴──────────────────────┼────────────────────┤
│ 身份供应与本局身份构成区            │ 最终牌堆生成／送出区   │
├───────────────────────────────────┴────────────────────┤
│ 排除区｜暂存区｜返回原牌库区｜状态与数量提示             │
└────────────────────────────────────────────────────────┘
```

牌库桌应保留足够的自由操作空间，不要用大量Holder铺满全部桌垫。不同功能区同时使用标题、图标、边框和半透明底色区分，不能只依赖颜色。

## 5. 武将牌库浏览

### 5.1 分类方式

首版至少支持按扩展包分类：

- 标准；
- 风；
- 火；
- 林；
- 山；
- 一将成名；
- SP；
- 其他已接入扩展。

后续可以增加势力、体力、版本或关键词筛选，但不得在首版引入复杂数据库和全文搜索依赖。

### 5.2 展示方式

不要一次铺开全部武将。推荐每页展示约 20–30 张正面武将牌，例如：

```text
5列 × 4行
6列 × 4行
```

每张牌支持：

- 正面浏览；
- 原生悬停／长按放大；
- 拖入本局候选区；
- 拖入排除区；
- 返回所属扩展；
- 清楚显示已选择、已排除或仍在牌库的状态。

展示区应保留卡牌间距，不能形成Pile，也不能让大量卡牌互相遮挡。

### 5.3 分页与切换

提供：

- 扩展标签；
- 上一页；
- 下一页；
- 当前页码；
- 当前扩展总数；
- 当前候选数量。

切换扩展或分页不得复制新卡牌。未展示的卡牌可以进入隐藏牌库Holder或使用显示状态控制。

## 6. 本局武将候选区

候选区用于在生成最终牌堆前核对本轮武将。

要求：

- 候选牌保持正面；
- 可以自由排列、比较和放大；
- 可以移除误选牌；
- 可以拖到排除区；
- 显示实时数量；
- 不自动决定本局应选多少张；
- 不自动按人数增删武将；
- 不自动去除所谓“不适合本局”的武将。

建议显示：

```text
本局武将候选：36张
```

### 6.1 生成最终武将牌堆

确认后执行“生成本局武将牌堆”：

1. 只收集候选区内的武将牌；
2. 在牌仍处于候选区时统一恢复为背面；
3. 收拢为真正的 VirtualTabletop 原生Pile；
4. 根据用户操作选择是否洗牌；
5. 放入“本局武将牌堆”Holder；
6. 更新候选区和最终牌堆的数量提示。

生成操作不得收集：

- 牌库浏览区中的牌；
- 排除区中的牌；
- 暂存区中的牌；
- 主桌上的牌；
- 其他类型牌库中的牌。

### 6.2 送入主桌

“送入主桌”将整个最终武将牌堆移动到主桌武将牌堆Holder。

要求：

- 使用真实Pile，不复制牌堆；
- 保持背面；
- 不自动抽取或发放武将；
- 不要求玩家手动把整叠牌拖过超大画布；
- 送出后更新牌库桌状态；
- 重复点击不得生成重复牌堆；
- 主桌与牌库桌之间的物理距离不得影响操作可靠性。

## 7. 身份牌供应与构成

身份牌采用“供应堆＋本局构成区”，不使用大面积平铺浏览。

供应区包含独立牌堆和数量提示：

```text
主公
忠臣
反贼
内奸
其他模式身份
```

玩家根据所采用的规则手动取出所需数量，放入本局身份构成区。

### 7.1 构成核对

构成区允许在准备阶段正面显示身份牌或使用数量标签进行核对，例如：

```text
主公 ×1
忠臣 ×1
反贼 ×2
内奸 ×1
```

系统不判断该构成是否符合任何人数规则。

### 7.2 生成身份牌堆

点击“盖回并洗牌”：

1. 只收集本局身份构成区中的身份牌；
2. 统一恢复背面；
3. 收拢为Pile；
4. 洗牌；
5. 移入最终身份牌堆Holder；
6. 允许随后送入主桌。

身份牌送入主桌后，不得通过牌库桌、房主权限、放大功能或其他菜单查看已经分发的身份正面。

## 8. 游戏牌与扩展牌编组

牌库桌后续可以用相同流程管理：

- 标准游戏牌；
- 军争扩展；
- 特殊模式牌；
- 自定义扩展；
- 标记牌；
- 体力牌；
- 其他公共组件。

统一流程：

```text
选择牌包
→ 加入本局候选
→ 核对数量
→ 生成牌堆
→ 盖回并洗牌
→ 送入主桌
```

首版优先完成武将牌与身份牌。游戏牌扩展编组作为后续子阶段，不得阻塞基础牌库桌原型验收。

## 9. 排除区、暂存区与返回原牌库

### 9.1 排除区

用于明确不加入本局的牌：

- 禁用武将；
- 当前模式不使用的牌；
- 重复版本；
- 玩家人工决定排除的内容。

排除区中的牌不参与生成、洗牌或送入主桌。

### 9.2 暂存区

用于尚未决定是否选入的牌。暂存区不参与生成最终牌堆。

### 9.3 返回原牌库

提供“返回原牌库”功能，将牌送回其原始扩展或供应区。不得简单全部堆到一个通用回收堆中，也不要求用户长距离手动拖回。

## 10. 卡牌来源与状态元数据

每张可编组卡牌建议保存：

```ts
libraryType: 'general' | 'identity' | 'playing' | 'token'
sourcePack: string
homeZone: string
poolState: 'library' | 'candidate' | 'excluded' | 'staging' | 'final' | 'active'
```

用途：

- 返回正确扩展；
- 防止重复加入；
- 统计候选数量；
- 重置牌库桌；
- 判断哪些牌已送入主桌；
- 避免卡牌脱离来源后无法归位；
- 在超大桌布中定位和恢复异常卡牌。

不得默认使用克隆卡牌方案。优先移动真实卡牌对象，保证每张实体牌在同一时刻只存在一份。

## 11. 完整牌库浏览器

实体牌库桌适合浏览当前扩展和候选牌，但牌量很大时可以增加本地 `INPUT choose` 浏览器。

用途：

- 快速浏览某扩展；
- 在弹层中查看牌面；
- 选择一张或多张牌；
- 将选择结果定位或移动到候选区。

要求：

- 弹层仅当前操作者可见；
- 不在共享桌面同步创建大型菜单；
- 选择结果不得克隆重复实体牌；
- 已在候选、排除或主桌中的牌应显示相应状态或禁止重复选取；
- `INPUT`浏览器作为效率工具，不能替代实体候选区和最终牌堆核对流程。

## 12. 权限设计

### 12.1 所有人可执行

默认允许所有玩家：

- 平移到牌库桌；
- 查看公开牌库；
- 放大公开牌；
- 查看候选和排除状态。

### 12.2 可配置编组模式

提供两种模式：

```text
共同编组：所有已入座玩家可添加或移除候选牌
房主编组：普通玩家只读，房主负责修改候选牌
```

### 12.3 房主操作

房主可以：

- 锁定／解锁牌库桌；
- 生成最终牌堆；
- 洗牌；
- 送入主桌；
- 重置编组桌；
- 恢复异常归位。

房主不得：

- 查看玩家手牌正面；
- 查看已分发身份；
- 绕过私密展示区；
- 在对局中无提示重置真实卡牌。

危险操作必须二次确认。

## 13. 重置、归位与遗失防护

牌库桌至少提供三种明确不同的恢复动作。

### 13.1 清空候选

将候选区、排除区和暂存区的牌返回各自原牌库，不影响主桌和最终牌堆。

### 13.2 重置牌库桌

恢复所有尚未送入主桌的牌库卡牌、分页、筛选和区域位置，不处理已经进入主桌或玩家区域的牌。

### 13.3 完整恢复初始状态

将主桌和牌库桌共同恢复到初始状态。必须二次确认，并明确提示会影响正在进行的牌局。

### 13.4 超大桌布防遗失

增加诊断与保护：

- 所有功能区域位于安全边距内；
- 卡牌拖动不得越出Board有效范围；
- 对靠近极端边缘的卡牌提供低调视觉警示；
- 使用 `homeZone` 和 `poolState` 判断归属；
- 可提供“检查异常卡牌”操作，列出或高亮脱离已知区域的牌；
- 不得自动回收主桌上正在使用的正常自由卡牌；
- 恢复操作不得静默复制、删除或丢失卡牌。

## 14. Holder与洗牌边界

- 主桌摸牌堆、武将牌堆和最终身份牌堆使用真正的 `pileZone`。
- 牌库浏览网格不得形成Pile。
- 候选区、排除区和暂存区采用自由或明确排列区域。
- 主桌待回收区只处理主桌待回收牌。
- 牌库桌生成操作只处理对应候选区。
- 主桌洗牌不得收集牌库桌、过渡走廊或备牌托盘中的牌。
- 牌库桌重置不得处理玩家手牌、私密展示区或主桌活动牌。

## 16. 测试计划

建议新增或调整：

```text
tests/
├── continuous-board-size.test.ts
├── continuous-board-bounds.test.ts
├── main-library-separation.test.ts
├── library-card-uniqueness.test.ts
├── general-candidate.test.ts
├── identity-composer.test.ts
├── final-deck-assembly.test.ts
├── shuffle-scope.test.ts
├── library-reset.test.ts
├── library-permissions.test.ts
└── lost-card-diagnostics.test.ts
```

自动测试至少验证：

- Board尺寸有效且处于项目限定范围；
- 连续背景覆盖完整Board；
- 主桌、过渡区和牌库桌不越界；
- 主桌与牌库桌的功能区域不重叠；
- 过渡走廊无牌堆和玩家模块；
- 卡牌在牌库、候选、最终牌堆和主桌之间保持唯一；
- 主桌与牌库桌的洗牌范围严格隔离；
- 送入主桌不会复制牌堆；
- 返回原牌库能根据 `homeZone` 正确归位；
- 隐私牌不会因为超大桌布或牌库操作泄漏。

人工测试至少验证：

- 两个浏览器会话可以分别停留在主桌和牌库桌；
- 一个玩家的平移和缩放不强制改变其他玩家镜头；
- 常见PC分辨率下可在两桌之间可靠导航；
- 触屏缩放和平移不会频繁误拖卡牌；
- 长距离送入主桌和返回牌库操作可靠；
- 桌面缩放后区域标题和方向提示仍可识别；
- 不会因Board过大导致牌和按钮不可操作。

## 18. 验收标准

牌库与编组桌完成时必须满足：

- 主桌与牌库桌位于同一连续Board并可独立浏览；
- Board尺寸适中，不依赖真正无限坐标或核心源码修改；
- 两个玩家可分别查看主桌与牌库桌，互不强制同步镜头；
- 桌布视觉连续，没有明显的大画布外框干扰；
- 主桌、牌库桌和过渡走廊具有清楚的视觉层级；
- 武将牌可以按扩展分页正面浏览和放大；
- 玩家可以人工选择、排除、暂存和比较武将；
- 候选区可以生成真正背面重叠的武将Pile；
- 最终牌堆可以作为同一真实对象送入主桌；
- 身份牌可以人工构成、核对、盖回、洗牌并送入主桌；
- 牌库、候选、排除、最终牌堆和主桌之间不存在重复实体牌；
- 主桌洗牌和牌库生成的作用范围完全隔离；
- 普通玩家和房主都不能借牌库桌绕过手牌或身份隐私；
- 重置操作不会丢牌、复制牌或误处理正在主桌使用的牌；
- 常见PC分辨率下能可靠导航，移动端有可用降级方案；
- 构建、验证和自动测试通过；
- 至少使用两个不同玩家会话完成导航、选择、生成、送入和隐私人工测试。

## 19. 当前边界

本计划不包含：

- 真正无限坐标、动态扩展画布或负坐标；
- 修改VirtualTabletop上游源码；
- 自动判断三国杀人数规则；
- 自动决定身份构成；
- 自动推荐武将；
- 自动平衡或禁用武将；
- 技能、距离、体力、伤害、回合或胜负判定；
- 通过房主权限查看私密牌；
- 默认克隆完整牌库。

牌库桌的职责仅是提供清晰、安全、可恢复的人工牌库浏览与牌堆编组工具。超大桌布的职责仅是提供足够空间和独立视图，不改变游戏规则与隐私边界。

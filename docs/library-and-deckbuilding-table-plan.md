# 牌库与编组桌开发计划

> 适用分支：`refactor/native-vtt-4p-prototype`  
> 项目原则：弱规则、弱状态、强同步、强可见性控制。  
> 本计划描述主游戏桌之外的第二张功能桌，用于浏览牌库、选择本局牌张、构成牌堆并送入主桌。

## 1. 背景与目标

当前主桌边缘的备牌托盘只适合存放少量备用牌或若干完整牌堆。当武将牌、身份牌和扩展牌数量增加后，所有牌叠放在托盘中会导致以下问题：

- 无法快速浏览武将正面；
- 难以按扩展包、势力或其他元数据筛选；
- 不便比较和选择本轮使用的武将；
- 身份牌构成不容易人工核对；
- 把选中牌重新收拢、盖回、洗牌并送入主桌的流程繁琐；
- 主桌被大量准备阶段组件挤占。

因此新增一张独立的 **牌库与编组桌**，承担：

```text
浏览牌库
→ 选择本局候选牌
→ 排除或暂存牌
→ 核对本局构成
→ 收拢、盖回和洗牌
→ 送入主游戏桌
```

第二张桌不执行三国杀规则判断，也不根据人数自动决定武将数量、身份构成或扩展包组合。

## 2. 核心架构：同房间双桌切换

第二张桌不是独立房间，也不是另一个 `.vtt` 文件，而是同一个房间内的一组独立桌面组件。

```text
同一房间
├── 主游戏桌组件组
└── 牌库与编组桌组件组
```

顶部或侧边提供：

```text
打开牌库桌
返回主桌
```

切换时只改变组件组的显示状态和视图焦点，不执行以下操作：

- 不重置牌局；
- 不洗牌；
- 不改变卡牌正反面；
- 不改变卡牌所有者；
- 不改变手牌和私密信息；
- 不重新生成或复制整套牌库。

主桌和牌库桌共享同一批真实卡牌对象，因此选中的武将牌堆、身份牌堆和游戏牌堆可以直接送入主桌。

### 2.1 双桌显示要求

- 默认进入主游戏桌。
- 打开牌库桌时隐藏主桌中不需要持续显示的大型公共组件。
- 玩家个人手牌和已经分发的私密牌不得因切换桌面而泄漏或改变归属。
- 已开始对局后，牌库桌可以被房主锁定为只读或禁止进入。
- 两张桌不得同时完整铺开在同一超大画布上，避免缩小、滚动和越界问题。

## 3. 牌库桌总体布局

建议结构：

```text
┌────────────────────────────────────────────────────────┐
│ 返回主桌｜武将库｜身份库｜游戏牌库｜扩展管理｜重置编组桌 │
├────────────┬──────────────────────┬────────────────────┤
│ 分类／扩展栏 │ 牌库浏览与分页展示区   │ 本局候选区           │
│            │                      │                    │
├────────────┴──────────────────────┼────────────────────┤
│ 身份供应与本局身份构成区            │ 最终牌堆生成／送出区   │
├───────────────────────────────────┴────────────────────┤
│ 排除区｜暂存区｜返回原牌库区｜状态与数量提示             │
└────────────────────────────────────────────────────────┘
```

牌库桌应保留大量空白操作空间，不要用大量纯白矩形铺满画面。不同功能区域使用半透明底板、标题、图标和不同边框共同区分。

## 4. 武将牌库浏览

### 4.1 分类方式

首版至少支持按扩展包分类：

- 标准；
- 风；
- 火；
- 林；
- 山；
- 一将成名；
- SP；
- 其他已接入扩展。

后续可以增加势力、体力、版本或关键词筛选，但不得在首版引入复杂数据库和全文搜索依赖。

### 4.2 展示方式

不要一次铺开全部武将。推荐每页展示约 20–30 张正面武将牌，例如：

```text
5列 × 4行
6列 × 4行
```

每张牌支持：

- 正面浏览；
- 原生悬停／长按放大；
- 拖入本局候选区；
- 拖入排除区；
- 返回所属扩展；
- 清楚显示已选择、已排除或仍在牌库的状态。

展示区应保留卡牌间距，不能形成Pile，也不能让大量卡牌互相遮挡。

### 4.3 分页与切换

提供：

- 扩展标签；
- 上一页；
- 下一页；
- 当前页码；
- 当前扩展总数；
- 当前候选数量。

切换扩展或分页不得复制新卡牌。未展示的卡牌可以进入隐藏牌库Holder或使用显示状态控制。

## 5. 本局武将候选区

候选区用于在生成最终牌堆前核对本轮武将。

要求：

- 候选牌保持正面；
- 可以自由排列、比较和放大；
- 可以移除误选牌；
- 可以拖到排除区；
- 显示实时数量；
- 不自动决定本局应选多少张；
- 不自动按人数增删武将；
- 不自动去除所谓“不适合本局”的武将。

建议显示：

```text
本局武将候选：36张
```

### 5.1 生成最终武将牌堆

确认后执行“生成本局武将牌堆”：

1. 只收集候选区内的武将牌；
2. 在牌仍处于候选区时统一恢复为背面；
3. 收拢为真正的VirtualTabletop原生Pile；
4. 根据用户操作选择是否洗牌；
5. 放入“本局武将牌堆”Holder；
6. 更新候选区和最终牌堆的数量提示。

生成操作不得收集：

- 牌库浏览区中的牌；
- 排除区中的牌；
- 暂存区中的牌；
- 主桌上的牌；
- 其他类型牌库中的牌。

### 5.2 送入主桌

“送入主桌”将整个最终武将牌堆移动到主桌武将牌堆Holder。

要求：

- 使用真实Pile，不复制牌堆；
- 保持背面；
- 不自动抽取或发放武将；
- 不自动切回主桌之前修改牌序；
- 送出后更新牌库桌状态；
- 重复点击不得生成重复牌堆。

## 6. 身份牌供应与构成

身份牌采用“供应堆＋本局构成区”，不使用大面积平铺浏览。

供应区包含独立牌堆和数量提示：

```text
主公
忠臣
反贼
内奸
其他模式身份
```

玩家根据所采用的规则手动取出所需数量，放入本局身份构成区。

### 6.1 构成核对

构成区允许在准备阶段正面显示身份牌或使用数量标签进行核对，例如：

```text
主公 ×1
忠臣 ×1
反贼 ×2
内奸 ×1
```

系统不判断该构成是否符合任何人数规则。

### 6.2 生成身份牌堆

点击“盖回并洗牌”：

1. 只收集本局身份构成区中的身份牌；
2. 统一恢复背面；
3. 收拢为Pile；
4. 洗牌；
5. 移入最终身份牌堆Holder；
6. 允许随后送入主桌。

身份牌送入主桌后，不得通过牌库桌、房主权限、放大功能或其他菜单查看已经分发的身份正面。

## 7. 游戏牌与扩展牌编组

第二张桌后续可以用相同流程管理：

- 标准游戏牌；
- 军争扩展；
- 特殊模式牌；
- 自定义扩展；
- 标记牌；
- 体力牌；
- 其他公共组件。

统一流程：

```text
选择牌包
→ 加入本局候选
→ 核对数量
→ 生成牌堆
→ 盖回并洗牌
→ 送入主桌
```

首版优先完成武将牌与身份牌。游戏牌扩展编组作为后续子阶段，不得阻塞牌库桌基础原型验收。

## 8. 排除区、暂存区与返回原牌库

### 8.1 排除区

用于明确不加入本局的牌：

- 禁用武将；
- 当前模式不使用的牌；
- 重复版本；
- 玩家人工决定排除的内容。

排除区中的牌不参与生成、洗牌或送入主桌。

### 8.2 暂存区

用于尚未决定是否选入的牌。暂存区不参与生成最终牌堆。

### 8.3 返回原牌库

提供“返回原牌库”功能，将牌送回其原始扩展或供应区。不得简单全部堆到一个通用回收堆中。

## 9. 卡牌来源与状态元数据

每张可编组卡牌建议保存：

```ts
libraryType: 'general' | 'identity' | 'playing' | 'token'
sourcePack: string
homeZone: string
poolState: 'library' | 'candidate' | 'excluded' | 'staging' | 'final' | 'active'
```

用途：

- 返回正确扩展；
- 防止重复加入；
- 统计候选数量；
- 重置牌库桌；
- 判断哪些牌已送入主桌；
- 避免卡牌脱离来源后无法归位。

不得默认使用克隆卡牌方案。优先移动真实卡牌对象，保证每张实体牌在同一时刻只存在一份。

## 10. 完整牌库浏览器

物理牌库桌适合浏览当前扩展和候选牌，但牌量很大时可以增加本地 `INPUT choose` 浏览器。

用途：

- 快速浏览某扩展；
- 在弹层中查看牌面；
- 选择一张或多张牌；
- 将选择结果定位或移动到候选区。

要求：

- 弹层仅当前操作者可见；
- 不在共享桌面同步创建大型菜单；
- 选择结果不得克隆重复实体牌；
- 已在候选、排除或主桌中的牌应显示相应状态或禁止重复选取；
- `INPUT`浏览器作为效率工具，不能替代实体候选区和最终牌堆核对流程。

## 11. 权限设计

### 11.1 所有人可执行

默认允许所有玩家：

- 打开牌库桌；
- 查看公开牌库；
- 放大公开牌；
- 查看候选和排除状态。

### 11.2 可配置编组模式

提供两种模式：

```text
共同编组：所有已入座玩家可添加或移除候选牌
房主编组：普通玩家只读，房主负责修改候选牌
```

### 11.3 房主操作

房主可以：

- 锁定／解锁牌库桌；
- 生成最终牌堆；
- 洗牌；
- 送入主桌；
- 重置编组桌；
- 恢复异常归位。

房主不得：

- 查看玩家手牌正面；
- 查看已分发身份；
- 绕过私密展示区；
- 在对局中无提示重置真实卡牌。

危险操作必须二次确认。

## 12. 重置与恢复

牌库桌至少提供三种明确不同的恢复动作：

### 12.1 清空候选

将候选区、排除区和暂存区的牌返回各自原牌库，不影响主桌和最终牌堆。

### 12.2 重置牌库桌

恢复所有尚未送入主桌的牌库卡牌、分页、筛选和区域位置，不处理已经进入主桌或玩家区域的牌。

### 12.3 完整恢复初始状态

将主桌和牌库桌共同恢复到初始状态。必须二次确认，并明确提示会影响正在进行的牌局。

任何重置都不得静默复制、删除或丢失卡牌。

## 13. 视觉设计

牌库桌需要与主桌保持同一整体风格，但功能层次更加清楚：

- 分类栏：低饱和木质或金属标签；
- 浏览区：中性半透明底板；
- 候选区：暖色或金色边框；
- 排除区：暗红或斜纹边框；
- 暂存区：灰蓝色虚线边框；
- 最终牌堆区：清楚的牌堆图标和数量；
- 身份构成区：锁或身份图标；
- 已送入主桌状态：明显但不刺眼的完成标记。

不能只依赖颜色，还应同时使用文字、图标和边框样式。避免大面积纯白底板。

## 15. 分阶段实施

### Phase L0：静态双桌原型

- [ ] 创建牌库桌背景和区域；
- [ ] 实现主桌／牌库桌切换；
- [ ] 确保切换不改变卡牌和私密状态；
- [ ] 放入少量占位武将与身份牌。

### Phase L1：武将浏览与候选区

- [ ] 按扩展分类；
- [ ] 正面网格展示；
- [ ] 分页；
- [ ] 候选区；
- [ ] 排除区和暂存区；
- [ ] 返回原牌库。

### Phase L2：武将牌堆生成与送入主桌

- [ ] 收集候选区；
- [ ] 盖回；
- [ ] 收拢为Pile；
- [ ] 洗牌；
- [ ] 送入主桌；
- [ ] 防止重复生成和重复送出。

### Phase L3：身份牌构成

- [ ] 身份供应堆；
- [ ] 本局身份构成区；
- [ ] 数量核对；
- [ ] 盖回并洗牌；
- [ ] 送入主桌。

### Phase L4：权限、恢复与人工验收

- [ ] 共同编组／房主编组；
- [ ] 牌库桌锁定；
- [ ] 三种重置等级；
- [ ] 多浏览器同步；
- [ ] 卡牌唯一性；
- [ ] 隐私与放大验证。

### 后续候选

- 游戏牌扩展编组；
- `INPUT choose`完整牌库浏览器；
- 更丰富的筛选；
- 保存常用牌组预设；
- 导入／导出本局编组清单。

保存预设只记录卡牌标识和扩展选择，不复制实体卡牌，也不自动覆盖当前牌局。

## 16. 验收标准

牌库与编组桌完成时必须满足：

- 可以在同一房间内安全切换主桌和牌库桌；
- 切换不影响玩家手牌、身份、卡牌归属和正反面；
- 武将牌可以按扩展分页正面浏览和放大；
- 玩家可以人工选择、排除、暂存和比较武将；
- 候选区可以生成真正背面重叠的武将Pile；
- 最终牌堆可以作为同一真实对象送入主桌；
- 身份牌可以人工构成、核对、盖回、洗牌并送入主桌；
- 牌库、候选、排除、最终牌堆和主桌之间不存在重复实体牌；
- 普通玩家和房主都不能借牌库桌绕过手牌或身份隐私；
- 重置操作不会丢牌、复制牌或误处理正在主桌使用的牌；
- 常见PC分辨率下不需要同时浏览两张超大桌面；
- 构建、验证和自动测试通过；
- 至少使用两个不同玩家会话完成切换、选择、生成、送入和隐私人工测试。

## 17. 当前边界

本计划不包含：

- 自动判断三国杀人数规则；
- 自动决定身份构成；
- 自动推荐武将；
- 自动平衡或禁用武将；
- 技能、距离、体力、伤害、回合或胜负判定；
- 通过房主权限查看私密牌；
- 修改VirtualTabletop上游源码；
- 默认克隆完整牌库。

牌库桌的职责仅是提供清晰、安全、可恢复的人工牌库浏览与牌堆编组工具。

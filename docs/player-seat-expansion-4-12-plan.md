# 4–12 人通用席位扩展详细计划

> 适用分支：`feature/library-and-deckbuilding-table`  
> 适用阶段：玩家人数与席位管理扩展  
> 项目原则：弱规则、弱状态、强同步、强可见性控制。  
> 本计划只扩展玩家席位、玩家模块显示与管理能力；现有桌面、牌务区、备牌托盘、备牌面板及固定游戏主牌流程保持不变。

## 1. 最终目标

将当前固定 4 人原型扩展为一个单一的 **4–12 人通用房间**：

```text
默认开放席位：4
最少开放席位：4
最大开放席位：12
```

房间内部预先创建 12 套完整玩家模块，但初始只显示前 4 套。房主可在房间内逐个增加开放席位；玩家可以在任意可见且空闲的 Seat 中自行选择入座，并自行或由房主移动玩家模块到合适位置。

本计划不要求在创建房间前确定最终人数，也不发布 4P、5P、6P 等多套独立 `.vtt` 文件。

核心使用流程：

```text
创建房间
→ 默认开放 4 席
→ 玩家陆续进入
→ 不够时房主点击“增加席位”
→ 新玩家模块显示在候场位置
→ 玩家选择任意可见空席入座
→ 房主或玩家移动模块
→ 必要时统一缩放模块
→ 锁定布局
```

## 2. 已冻结的产品边界

### 2.1 桌面保持现状

以下内容不因玩家人数变化而修改：

- Board 继续使用当前 `1800 × 1200`；
- 中央摸牌堆、快捷洗牌区和待回收区位置不变；
- 个人手牌区位置与尺寸不变；
- 备牌托盘位置、尺寸、四个牌槽及专属洗牌按钮不变；
- 覆盖式备牌面板位置、尺寸与打开方式不变；
- 固定游戏主牌继续直接位于摸牌堆；
- 不恢复超大连续桌布，不增加第二张桌面；
- 不修改 VirtualTabletop 上游源码。

### 2.2 玩家模块结构保持一致

所有 12 个玩家模块继续使用同一套结构：

```text
玩家模块根节点
├── Seat
├── 玩家标题
├── 离座按钮
├── 私密视角按钮
├── 手牌数量
├── 对外展示区
├── 私密展示区
└── 盲选相关控件
```

不制作标准、紧凑、密集三套不同模块，也不因人数增加而删减功能。

### 2.3 允许自由移动和轻微重叠

默认布局只负责让新增模块可以被看到、抓取和入座，不承担永久最优排版责任。

允许：

- 玩家模块边缘轻微重叠；
- 玩家模块与普通公共桌面区域相交；
- 高人数时部分模块相互覆盖；
- 房主和玩家自行拖动模块；
- 通过全局或单模块缩放缓解拥挤。

不允许：

- 新模块完全生成在 Board 外；
- 模块标题栏和 Seat 按钮全部被覆盖，无法抓取；
- 模块被隐藏时仍有玩家或卡牌但没有安全提示；
- 重叠或缩放破坏 Seat、Owner 或私密可见性。

### 2.4 不自动处理人数相关游戏规则

系统不自动：

- 配置身份牌比例；
- 判断某人数应使用哪些身份；
- 发身份牌；
- 分配阵营；
- 判断胜负；
- 限制模式；
- 校验身份牌数量是否足够。

当前资源中身份牌数量不足以覆盖所有 12 人玩法时，仍允许使用自定义模式、团队模式或玩家人工补充资源。

## 3. 总体技术方案

### 3.1 预创建 12 套玩家模块

构建 `.vtt` 时一次性生成：

```text
player-module-1  … player-module-12
seat-1           … seat-12
public-zone-1    … public-zone-12
private-zone-1   … private-zone-12
hand-count-1     … hand-count-12
blind-zone-1     … blind-zone-12
```

其中：

```text
player-module-1 … player-module-4   display = true
player-module-5 … player-module-12  display = false
```

不在运行时动态创建或删除 Widget。

这样可以保证：

- 所有 ID 构建时确定；
- 私密链接构建时验证；
- 多客户端同步简单；
- 不会因删除模块导致内部卡牌丢失；
- 所有 12 个模块均可纳入自动测试；
- Routine 不需要运行时生成新对象。

### 3.2 开放席位与已入座人数分离

系统必须区分：

```text
开放席位数：当前显示多少个玩家模块
已入座人数：当前多少个 Seat 绑定了玩家
```

示例：

```text
开放席位：7 / 12
已入座：5
```

不能根据在线人数自动增减席位，因为房间中可能存在观察者、未入座玩家或临时掉线玩家。

### 3.3 单一通用版本

构建产物建议改为：

```text
Sanguosha-Manual-4-12P.vtt
```

游戏信息：

```text
players: "4–12"
variant: "4–12 人通用人工桌面"
```

不再维护七个或九个不同人数版本。

## 4. 房主玩家管理面板

### 4.1 管理入口

在现有顶部房主工具栏增加一个紧凑入口：

```text
👥 玩家管理
```

点击后展开玩家管理面板，而不是把全部按钮直接挤入主工具栏。

建议面板内容：

```text
开放席位：4 / 12
已入座：3

[＋ 增加席位]
[－ 关闭最后空席]

全部玩家模块大小：
[75%] [90%] [100%]

[解锁布局] [锁定布局]
```

### 4.2 增加席位

点击“增加席位”时：

1. 查找编号最小的隐藏玩家模块；
2. 将该模块及其必要子控件设为可见；
3. 模块继承当前全局玩家模块缩放比例；
4. 模块显示在预设候场位置；
5. 将模块置于较高 z 层，确保标题栏可以抓取；
6. 更新开放席位计数；
7. 不自动绑定玩家；
8. 不移动已有玩家模块；
9. 不自动缩小全部模块；
10. 不自动重新排列桌面。

达到 12 席后：

- 按钮应禁用，或
- 点击后提示“已达到 12 席上限”。

### 4.3 玩家自由选择空席

玩家可在任意可见且空闲的 Seat 中入座。

不强制：

- 第五个进入房间的玩家必须坐 `seat-5`；
- 玩家按模块编号顺序入座；
- 房主自动分配座位。

现有“一名玩家只能占用一个 Seat”和“已占用 Seat 不允许其他玩家覆盖”的安全逻辑继续保留，并扩展到 12 个 Seat。

### 4.4 玩家离座

玩家离座后：

```text
Seat 变为空
玩家模块继续显示
模块内卡牌不自动清理
模块不自动关闭
```

房主可决定：

- 保留该模块等待玩家返回；
- 让其他玩家入座；
- 清理模块后关闭空席。

## 5. 新增模块候场位置

### 5.1 原则

不为 4–12 每个人数设计独立精确布局。

新增模块的候场位置只需满足：

- 根节点位于 Board 内；
- 标题栏可见；
- Seat 可点击；
- 不完全遮住已有模块；
- 房主或玩家可立即拖动。

### 5.2 推荐候场策略

预设 8 个隐藏模块的初始位置分布在桌面四边：

```text
模块 5–6：上边缘候场
模块 7–8：右边缘候场
模块 9–10：下边缘候场
模块 11–12：左边缘候场
```

允许这些候场位置与当前模块轻微重叠。

新增模块应优先让标题栏暴露在已有模块之外。必要时使用少量坐标错位，例如每个候场模块在 x/y 上偏移 20–30 像素。

### 5.3 不自动重排已有模块

“增加席位”不能：

- 把已被玩家人工调整的模块重新排成默认位置；
- 改变已有模块缩放比例；
- 移动摸牌堆或备牌托盘；
- 覆盖玩家自定义布局。

## 6. 玩家模块缩放

### 6.1 全局缩放

房主可一键设置全部开放玩家模块：

```text
75%
90%
100%
```

可保留 115% 作为单模块放大档位，但不建议作为全局预设。

全局缩放只作用于：

```text
当前开放的 player-module-N 根节点
```

不作用于：

- 隐藏模块；
- 摸牌堆；
- 备牌托盘；
- 备牌面板；
- 手牌区；
- 房主工具栏。

### 6.2 新模块继承当前比例

维护一个共享属性：

```ts
globalPlayerModuleScale: 0.75 | 0.9 | 1.0
```

新增席位显示时，目标模块直接使用该比例。

### 6.3 单模块缩放

继续允许：

- 模块所属玩家缩放自己的模块；
- 房主缩放任意模块。

建议单模块档位：

```text
75% / 90% / 100% / 115%
```

缩放必须设置在玩家模块根节点上，所有内部控件和卡牌同步缩放。

### 6.4 缩放原点

所有玩家模块统一：

```ts
scale: 1,
css: {
  transformOrigin: 'top left',
}
```

避免缩放后模块中心漂移或遮挡范围不可预测。

## 7. 布局锁定与移动权限

### 7.1 布局编辑流程

推荐流程：

```text
房主解锁布局
→ 增加席位
→ 玩家或房主移动模块
→ 必要时调整缩放
→ 房主锁定布局
```

### 7.2 锁定对象

布局锁定集合由固定数组改为动态生成：

```ts
[
  ...openPlayerModuleIds,
  'reserve-tray',
]
```

隐藏模块不需要参与可移动状态切换，但其默认状态应保持一致，以便显示后继承当前布局模式。

### 7.3 玩家能否移动自己的模块

建议保留两种模式：

```text
全局布局模式：房主解锁后可整体整理
个人调整模式：所属玩家可调整自己的模块
```

若 VirtualTabletop 的权限粒度不方便实现，首版可继续使用现有“解锁后模块可移动、锁定后全部不可移动”的简单机制。

## 8. 安全关闭席位

### 8.1 关闭席位不是删除模块

关闭席位只执行：

```text
安全检查
→ display = false
→ 更新开放席位计数
```

不删除 Widget，不清除 ID，不移除 Routine。

### 8.2 快速关闭最后空席

房主工具栏中的“关闭最后空席”按以下顺序检查：

```text
从编号最大的开放模块开始
→ 找到第一个满足安全条件的空模块
→ 关闭该模块
```

不能单纯把开放席位数减一后直接隐藏最高编号模块。

### 8.3 指定关闭某一席

每个玩家模块标题栏建议增加一个仅房主可见的小按钮：

```text
关闭空席
```

用于房主在自由移动布局中明确关闭某个具体模块。

### 8.4 关闭前安全条件

目标模块必须同时满足：

1. 对应 Seat 没有玩家；
2. 对外展示区没有卡牌或其他可移动物件；
3. 私密展示区没有卡牌；
4. 没有任何卡牌 Owner 指向该 Seat 的玩家；
5. 对应手牌数量为 0；
6. 盲选区已关闭；
7. 盲选区中没有临时操作状态；
8. 不存在正在拖动的子物件。

任何条件不满足时拒绝关闭，并显示简明原因。

### 8.5 最少保留 4 席

房主不能把开放席位减少到 4 以下。

达到 4 席时：

- “关闭最后空席”按钮禁用，或
- 点击提示“至少保留 4 个开放席位”。

## 9. Seat 与权限参数化

### 9.1 ID 生成工具

新增通用辅助函数：

```ts
export const seatIds = (count = 12) =>
  Array.from({ length: count }, (_, i) => `seat-${i + 1}`);

export const playerModuleIds = (count = 12) =>
  Array.from({ length: count }, (_, i) => `player-module-${i + 1}`);
```

### 9.2 离座 Routine

删除逐个维护的：

```text
leaveSeat1Routine
leaveSeat2Routine
leaveSeat3Routine
leaveSeat4Routine
```

改为：

```ts
createLeaveSeatRoutine(seatId)
```

构建玩家模块时按编号生成。

### 9.3 清空全部座位

改为：

```ts
createClearAllSeatsRoutine(12)
```

确认文字应为：

```text
将清理全部 12 个 Seat 的玩家占用状态。
```

隐藏模块中的 Seat 也应被清空，避免未来重新开放时出现残留玩家。

### 9.4 视角切换 Routine

继续使用生成式：

```ts
createTogglePerspectiveRoutine(playerNumber)
```

并确保支持 1–12。

权限规则保持：

- 本座玩家可以切换自己的私密区域预览；
- 房主管理入口可以切换显示状态；
- 房主仍不能绕过牌面隐私；
- 隐藏模块不显示视角按钮。

### 9.5 房主管理权限

首版可继续暂用 `seat-1` 作为管理者判断入口，但计划中应保留后续扩展：

```text
独立主持人标识
主持人移交
主持人不必占用 seat-1
```

多人扩展首版不强制同时完成主持人系统重构。

## 10. 个人手牌区扩展

### 10.1 关联全部 12 个 Seat

现有个人手牌 Holder 的：

```ts
onlyVisibleForSeat
linkedToSeat
```

扩展为 `seat-1` 至 `seat-12`。

### 10.2 手牌计数

生成：

```ts
createUpdateHandCountsRoutine(12)
```

为每个 Seat 建立独立集合和计数变量：

```text
seat1HandCards … seat12HandCards
seat1HandCount … seat12HandCount
```

### 10.3 隐藏模块与手牌

隐藏模块对应的 Seat 理论上应为空；关闭安全检查必须确保其没有手牌。

不能出现：

```text
隐藏 player-module-9
但仍有卡牌 owner = seat-9 玩家
```

### 10.4 多客户端隐私验收

至少验证：

- Seat 1；
- Seat 5；
- Seat 9；
- Seat 12；
- 观察者；
- 房主视角。

确保其他玩家和房主都不能通过手牌区、私密区或 enlarge 查看非所属牌面。

## 11. 盲选区扩展

### 11.1 当前规模

若每个玩家模块保留 10 张盲选代理，则 12 人共：

```text
12 × 10 = 120 个盲选代理物件
```

首版允许继续预创建并默认隐藏。

### 11.2 坐标改造

不能继续使用简单的：

```ts
x = baseX + index * 25
y = baseY + index * 18
```

否则 12 个盲选区可能大面积偏移或越界。

建议所有玩家共用有限的盲选候场区域，或按 3–4 个固定位置循环放置；同一时间只建议展开一个盲选区。

### 11.3 非目标

多人扩展首版不重写盲选代理为动态数量，也不实现自动映射真实手牌。

## 12. 当前代码需要重构的固定 4 人点

需要逐项移除：

- `createFourPlayerPrototype()`固定名称与固定循环；
- `PLAYER_MODULES`只有 4 个坐标；
- `allSeats`固定 `seat-1` 至 `seat-4`；
- `leaveSeatRoutines`固定 4 项；
- `perspectiveRoutines`固定 4 项；
- `clearAllSeatsRoutine`固定 4 个 Seat；
- `updateHandCountsRoutine`固定 1–4；
- `moduleIds`固定 4 个玩家模块；
- `arrangeLayoutRoutine`固定 4 套坐标；
- 验证器要求恰好 4 个 Seat；
- 测试循环固定 `n <= 4`；
- 构建文件名包含 `4P-Prototype`；
- 游戏描述固定“4 人”。

## 14. Routine 设计

### 14.1 增加席位

```ts
createOpenNextSeatRoutine({
  min: 4,
  max: 12,
  moduleIds,
  globalScaleControllerId,
});
```

逻辑：

```text
若开放数 >= 12 → 提示上限
否则找到最小隐藏模块
→ 设置 scale
→ 设置 display = true
→ 设置 z 到前层
→ 更新计数
```

### 14.2 关闭指定席位

```ts
createCloseSeatRoutine(playerNumber)
```

逻辑：

```text
检查 Seat
检查公开区
检查私密区
检查手牌 Owner
检查盲选区
→ 全部为空才隐藏
```

### 14.3 关闭最后空席

```ts
createCloseHighestAvailableSeatRoutine(12)
```

从 12 向 5 依次查找安全可关闭模块。

### 14.4 全局缩放

```ts
createScaleOpenPlayerModulesRoutine(0.75)
createScaleOpenPlayerModulesRoutine(0.9)
createScaleOpenPlayerModulesRoutine(1.0)
```

### 14.5 更新统计

```ts
createUpdateSeatCountsRoutine(12)
```

统计：

- display 为 true 的玩家模块数量；
- player 非空的 Seat 数量。

## 15. 验证器调整

### 15.1 构建错误

以下仍应阻止构建：

- Seat 总数不是 12；
- 玩家模块总数不是 12；
- 默认显示模块数不是 4；
- ID 重复；
- 父子引用失效；
- private-zone 链接到错误 Seat；
- hand-count 缺失；
- Routine 引用不存在的模块；
- 玩家模块根节点完全位于 Board 外；
- 隐藏模块默认仍为可交互显示状态；
- 开放席位上限不是 12；
- 增加席位可以超过 12；
- 减少席位可以低于 4。

### 15.2 不再属于构建错误

以下不应阻止构建：

- 玩家模块之间轻微重叠；
- 玩家模块与备牌托盘边缘相交；
- 玩家模块与中央区域边缘相交；
- 高人数候场位置不对称；
- 默认位置不是最终可用布局。

可将明显重叠输出为 Warning，但不能阻止 `.vtt` 生成。

## 19. 验收标准

计划完成后必须满足：

1. 只发布一个 4–12 人通用 `.vtt`；
2. 房间内部存在 12 套完整玩家模块；
3. 默认只显示 4 个模块；
4. 房主可逐个增加席位至 12；
5. 玩家可自由选择任意可见空 Seat；
6. 新增席位不自动重排现有桌面；
7. 桌面、摸牌堆、备牌托盘和备牌面板保持现状；
8. 房主可统一设置开放模块为 75%、90% 或 100%；
9. 玩家模块可自由移动，轻微重叠不会阻止构建；
10. 同一玩家不能占多个 Seat；
11. 隐藏模块不能被玩家入座；
12. 关闭席位前必须确认其无玩家、无公开牌、无私密牌、无手牌和无盲选状态；
13. 开放席位不能低于 4 或高于 12；
14. Seat 1、5、9、12 的隐私语义一致；
15. 房主不能绕过私密牌面；
16. 4 人现有功能无回归；
17. 12 人状态下仍可移动、缩放、入座、离座、统计手牌和同步；
18. 所有自动测试和构建验证通过。

## 21. 最终决策摘要

本项目的玩家人数扩展正式采用：

> **一个 4–12 人通用房间；构建时预创建 12 个完整玩家模块，默认显示 4 个。房主在房间内按需逐个开放席位，玩家可在任意可见空席中自行入座，并自由移动玩家模块。桌面保持现状，默认布局只提供可抓取的候场位置，不追求绝对无重叠；房主可统一缩放开放模块，关闭席位必须经过严格安全检查。**

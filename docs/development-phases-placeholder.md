# 三国杀人工结算 VirtualTabletop 游戏包开发计划

> 状态：已确认开发方向，等待按阶段实施  
> 项目仓库：`Cc-Cece/sanguosha-manual-vtt`  
> 上游参考：`ArnoldSmith86/virtualtabletop`、`libnoname/noname`  
> 当前用途：私人好友间非商业游玩

## 1. 项目目标

本项目开发一个可导入 VirtualTabletop.io 的三国杀人工结算游戏包，最终主要交付物为：

```text
dist/Sanguosha-Manual-Tabletop.vtt
```

游戏包支持 4–10 名玩家。VirtualTabletop 负责房间、多人同步、座位、牌堆、私密手牌、隐藏身份和桌面状态；玩家通过外部语音沟通，自行判断技能、目标、距离、响应、伤害和胜负，并手动完成结算。

本项目不尝试复刻无名杀的自动规则引擎，而是参考其卡牌、武将、身份模式、术语和界面组织，重新实现适合线上好友语音局的自由桌面。

## 2. 核心原则

### 2.1 弱规则、强状态、人工裁定

系统可以确认一张牌属于谁、位于哪个区域、是否公开，以及玩家当前体力和标记状态，但不判断某个操作是否符合三国杀规则。

示例：玩家可以把一张“杀”移入中央处理区并声明目标，但系统不判断是否轮到该玩家、攻击距离是否足够、本回合是否已经使用过“杀”或目标是否受技能保护。

### 2.2 只自动化桌面动作

允许实现：

- 洗牌、发牌和摸牌；
- 出牌、弃牌、展示、交牌；
- 将牌放到牌堆顶或牌堆底；
- 手动调整体力和体力上限；
- 翻面、横置、阵亡和标记；
- 声明当前使用牌、目标、响应和结算状态；
- 清理中央处理区和重置桌面。

禁止实现：

- 技能自动触发；
- 卡牌合法性判断；
- 攻击距离计算；
- 回合阶段强制；
- 自动响应链；
- 自动伤害和濒死结算；
- 自动手牌上限；
- 自动胜负判断；
- 无名杀事件树或技能执行框架。

### 2.3 源码生成，不维护巨型 JSON

游戏数据、布局、Widget、Routine、素材和变体必须分离。TypeScript 源码生成 VirtualTabletop 兼容 JSON，再打包为 `.vtt`。不得把最终 `0.json` 当作主要维护源。

### 2.4 两个上游仓库始终只读

- `../virtualtabletop`：运行平台、格式规范和示例来源；
- `../noname-main`：三国杀数据与交互参考。

所有新代码、提取结果、素材索引、测试和构建产物只能写入本仓库。

## 3. 首版范围

### 3.1 支持内容

- 4、5、6、7、8、9、10 人七种人数变体；
- 同一个 `.vtt` 包中选择人数变体；
- 参数化座位与玩家区域生成器；
- 私密手牌；
- 隐藏身份；
- 武将牌和技能文字显示；
- 游戏牌堆、弃牌堆和中央处理区；
- 装备区、判定区、武将附加牌区；
- 体力和体力上限；
- 横置、翻面、阵亡、伤害类型和自定义标记；
- 摸牌、出牌、弃牌、展示和交牌；
- 洗牌、发身份、发初始手牌和新游戏重置；
- 当前行动玩家和人工结算声明；
- PC 浏览器优先，兼顾平板和手机横屏；
- 本地构建、验证和导入测试。

### 3.2 首版不包含

- 内置语音或视频；
- 账号、好友、匹配、排行和战绩；
- 自动技能和完整规则引擎；
- AI 玩家；
- 公共服务器运营功能；
- 面向公众的素材授权和发布流程；
- 对 VirtualTabletop 核心源码的修改。

## 5. 构建与验证流程

```text
参考数据快照
    ↓
标准化 TypeScript 数据
    ↓
生成 4–10 人布局和 Widget
    ↓
生成 VirtualTabletop JSON 变体
    ↓
校验 ID、引用、权限、坐标和素材
    ↓
复制素材并生成归属清单
    ↓
压缩为 .vtt
    ↓
导入本地 VirtualTabletop
    ↓
多浏览器人工验收
```

建议最终命令：

```powershell
pnpm build
pnpm validate
pnpm test
pnpm check
```

`pnpm check` 必须在每个阶段完成前通过。

## 6. 阶段计划

## P0：格式和最小技术验证

### 目标

证明由本仓库生成的 `.vtt` 可以被本地 VirtualTabletop 正确导入，并验证私密信息和实时同步。

### 实施内容

1. 调研并记录当前 VirtualTabletop 的：
   - `.vtt` 压缩包结构；
   - `_meta.info` 元数据；
   - Seat、Holder、Deck、Card、Pile、Button 和 Routine 的关键属性；
   - 私密手牌及玩家归属机制；
   - 公共游戏包中的最小可用示例。
2. 定义最小 TypeScript Widget 类型。
3. 实现最小 JSON 生成器和 `.vtt` 打包脚本。
4. 制作三座位技术验证桌面：
   - 20 张占位牌；
   - 公共牌堆；
   - 三个私密手牌区；
   - 中央处理区；
   - 弃牌堆；
   - 每人一个体力计数器。
5. 实现最少操作：
   - 洗牌；
   - 摸一张；
   - 摸两张；
   - 从手牌出牌；
   - 移入弃牌堆；
   - 体力加减。
6. 使用至少两个独立浏览器会话测试不同座位。

### 交付物

- `dist/Sanguosha-Manual-P0.vtt`；
- 初版构建和验证脚本；
- P0 测试报告；
- 私密信息测试截图；
- 已确认的 VirtualTabletop 属性记录。

### 验收标准

- `.vtt` 可正常导入且无解析错误；
- 玩家只能看到自己的手牌；
- 另一玩家看不到手牌正面；
- 摸牌、出牌、弃牌和体力变化实时同步；
- 刷新或重新进入后桌面状态可恢复；
- Widget ID、素材路径和 JSON 结构自动校验通过；
- 两个上游目录无修改。

### 停止条件

P0 未通过前，不导入正式三国杀牌堆、武将或真实素材。

## P1：4–10 人参数化桌面

### 目标

建立统一的玩家区域和布局生成器，生成 4–10 人七个可选择变体。

### 实施内容

1. 定义统一玩家区域：
   - 座位；
   - 武将位；
   - 隐藏身份位；
   - 手牌区；
   - 装备区；
   - 判定区；
   - 武将附加牌区；
   - 体力、上限和标记；
   - 当前行动提示。
2. 设计参数化椭圆或环形布局算法。
3. 先实现三个代表布局：
   - 4 人：空间最宽松；
   - 8 人：常用多人局；
   - 10 人：空间最紧张。
4. 三个代表布局通过后，生成 5、6、7、9 人变体。
5. 设计三档玩家面板密度：
   - 4–6 人标准面板；
   - 7–8 人紧凑面板；
   - 9–10 人超紧凑面板。
6. 优先采用所有玩家看到同一张固定俯视桌面的方案。只有确认 VirtualTabletop 能稳定支持座位相对视角后，才评估“本地玩家始终位于下方”。
7. 建立坐标越界、区域重叠和最小可点击尺寸测试。

### 交付物

- 4–10 人布局生成器；
- 七个人数变体；
- 桌面与玩家区域占位素材；
- 布局截图矩阵；
- 布局自动测试。

### 验收标准

- 七个变体均能独立加载；
- 4、8、10 人桌面无严重重叠或越界；
- 其他人数由同一生成器稳定生成；
- 玩家区、公共区和牌堆易于区分；
- 10 人局在常见 PC 分辨率下仍可点击和辨认；
- 更改玩家区域组件时无需手工修改七套 JSON。

## P2：身份、基础牌堆和数据管线

### 目标

参考无名杀建立可追踪、可校验的基础三国杀数据，并完成身份和牌堆初始化。

### 实施内容

1. 只读分析无名杀中的：
   - 身份模式配置；
   - 基础牌堆；
   - 卡牌名称、类别、花色和点数；
   - 武将基础信息位置；
   - 中文术语和翻译数据。
2. 编写受控提取器，只提取已列入白名单的数据字段。
3. 将提取结果转换成本项目中间格式，不在运行时依赖无名杀。
4. 对 4–10 人建立：
   - 经核对的默认身份预设；
   - 可手动增减的自定义身份牌堆。
5. 导入首批基础牌堆：
   - 基本牌；
   - 普通锦囊；
   - 延时锦囊；
   - 装备牌。
6. 建立卡牌数量、花色、点数、图片引用和唯一 ID 校验。
7. 实现：
   - 洗牌；
   - 隐藏发身份；
   - 发初始手牌；
   - 重新收集和重置牌堆。

### 交付物

- 标准化卡牌数据；
- 身份预设与自定义配置；
- 数据提取器及来源记录；
- 牌堆与身份初始化 Routine；
- 数据校验测试。

### 验收标准

- 数据来源和对应参考文件可追踪；
- 默认身份配置经过人工核对；
- 身份牌仅所属玩家可见；
- 正式牌堆的数量、花色和点数校验通过；
- 发牌不会泄露其他玩家私密信息；
- 重置后所有牌能回归正确牌堆；
- 未导入任何技能执行代码或事件框架。

## P3：人工桌面操作与结算流程

### 目标

让玩家不进入编辑模式即可完成一局三国杀的大部分物理桌面动作。

### 实施内容

1. 玩家常用操作：
   - 摸 1、摸 2、摸 N 张；
   - 出牌至中央处理区；
   - 弃牌；
   - 展示指定牌；
   - 将牌交给指定玩家；
   - 将牌置于武将牌旁；
   - 将牌放到牌堆顶或底；
   - 从弃牌堆取回牌。
2. 状态操作：
   - 体力和体力上限加减；
   - 横置；
   - 翻面；
   - 阵亡；
   - 火焰、雷电、普通伤害标记；
   - 自定义数字或文字标记。
3. 公共结算区：
   - 当前使用牌；
   - 来源玩家；
   - 声明目标；
   - 等待响应；
   - 暂缓结算；
   - 已结算或已取消；
   - 一键清理至弃牌堆。
4. 当前行动玩家提示和手动切换。
5. 为高风险操作增加确认：
   - 全局重置；
   - 清空牌堆；
   - 批量公开手牌；
   - 删除或移动大量卡牌。
6. 所有快捷操作只改变桌面状态，不判断规则是否合法。

### 交付物

- 完整桌面动作 Routine；
- 中央人工结算区；
- 状态与标记组件；
- 操作说明；
- 单人桌面流程测试。

### 验收标准

- 玩家可在非编辑模式完成常见动作；
- 所有状态变化对全体玩家同步；
- 目标和响应状态清晰可见；
- 任何动作都不会自动判断规则；
- 误操作能够通过手动反向操作或 VirtualTabletop 状态机制纠正；
- 一局基础身份局不需要频繁进入编辑模式。

## P4：武将展示与好友局体验

### 目标

导入首批武将基础信息，并改善人工发动技能时的信息查看体验。

### 实施内容

1. 从无名杀中提取或人工整理：
   - 武将 ID；
   - 名称；
   - 势力；
   - 体力上限；
   - 技能名称；
   - 技能说明文字；
   - 来源包。
2. 不导入技能代码、触发条件程序或自动结算。
3. 建立武将选择区：
   - 公开或私密抽取；
   - 展示候选武将；
   - 将选中武将移到玩家区域；
   - 双将或自定义模式保留扩展空间，但首版不承诺完整支持。
4. 支持点击或悬停查看技能全文。
5. 提供武将专属附加牌和标记的通用放置区域。
6. 先选取一个有限、可核对的首批武将集合，不一次性导入无名杀全部武将。

### 交付物

- 首批武将数据与素材；
- 武将选择区；
- 技能文字查看组件；
- 武将数据来源清单；
- 武将显示和选择测试。

### 验收标准

- 武将信息清晰可读；
- 技能只展示文字，不执行效果；
- 选择和替换武将不会破坏座位状态；
- 技能说明、势力和体力等字段经过抽样核对；
- 首批武将范围足够进行完整好友测试局。

## 7. 测试策略

### 7.1 自动测试

每次构建至少验证：

- `.vtt` 为可解压 ZIP；
- 至少存在一个有效 JSON 变体；
- 4–10 人七个变体齐全；
- Widget ID 全局唯一；
- 所有父子、Holder、Seat 和资源引用存在；
- 所有坐标在桌面边界内；
- 玩家关键区域不发生超过阈值的重叠；
- 每个私密 Holder 都绑定正确 Seat；
- 卡牌数据数量、花色和点数符合源数据；
- 包内所有资源路径可解析；
- 不包含禁止导入的无名杀规则模块。

### 7.2 浏览器测试

至少使用：

- 两个独立浏览器或无痕会话；
- 两个不同座位；
- 一个刷新或断线重入场景。

P5 阶段增加 4、8、10 人多人实测。

### 7.3 人工验收

每阶段完成后由用户核对：

- 布局是否易读；
- 按钮是否过多；
- 手牌、装备和判定区是否容易操作；
- 人工结算是否流畅；
- 是否仍保持线下桌游感；
- 是否出现不希望的规则自动化。

未经用户确认，不进入下一阶段。

## 10. 主要风险与应对

### 10.1 VirtualTabletop 专用语法理解错误

应对：P0 只做最小包；所有关键属性从当前源码和可运行示例确认；每次新增复杂 Routine 都配套最小测试桌面。

### 10.2 10 人布局拥挤

应对：三档面板密度；先验收 4、8、10 人；9–10 人折叠次要信息；PC 优先。

### 10.3 隐藏信息泄漏

应对：多浏览器会话测试列为阶段阻断项；任何身份或手牌泄漏都必须先修复再继续。

### 10.4 无名杀数据规模过大

应对：白名单字段提取；先基础牌和有限武将；不扫描或转换全部技能逻辑；保留快照版本信息。

### 10.5 素材体积过大

应对：首版使用有限素材；统一尺寸和压缩；生成素材索引；在 P5 记录加载时间和包体积。

### 10.6 误操作难以恢复

应对：危险按钮确认；状态保存；清晰操作日志或桌面声明；提供反向操作；定期保留阶段可用包。

### 10.7 上游更新导致格式变化

应对：记录已验证的 VirtualTabletop 提交或版本；构建只针对已验证版本；升级前单独建立兼容性分支。

## 11. 完成定义

项目达到 v1.0 的条件：

- 文档、来源和已知限制齐全；
- 用户完成最终验收。

# 三国杀联网虚拟桌面开发计划

> 状态：开发方向已重新确认，按本计划分阶段实施  
> 项目仓库：`Cc-Cece/sanguosha-manual-vtt`  
> 目标平台：`ArnoldSmith86/virtualtabletop`  
> 内容参考：`libnoname/noname`  
> 桌面参考：Tabletop Simulator Workshop `504420279` 的只读解析结果  
> 当前用途：私人好友间非商业游玩

## 1. 项目定位

本项目开发一个可导入 VirtualTabletop.io 的三国杀联网虚拟桌面游戏包，最终主要交付物为：

```text
dist/Sanguosha-Manual-Tabletop.vtt
```

游戏包支持 4–10 名玩家。VirtualTabletop 只负责提供一张可以联网同步、隐藏手牌和身份、摆放与操作卡牌的虚拟桌子；玩家通过外部语音交流，自行判断规则并手动完成所有结算。

项目不复刻无名杀的自动规则引擎，也不把体力、横置、翻面、阵亡、当前回合等概念设计成必须由程序维护的抽象变量。游戏状态优先通过桌面物件的位置、遮挡、翻面、旋转、堆叠和可见性自然表达。

一句话定位：

> **弱规则、弱状态、强同步、强可见性控制。**

## 2. 核心设计原则

### 2.1 弱规则

系统不判断玩家行为是否合法，不实现：

- 技能自动触发；
- 卡牌使用条件；
- 攻击距离；
- 回合阶段限制；
- 使用次数限制；
- 自动响应链；
- 自动伤害、濒死或救援；
- 手牌上限；
- 自动胜负判断；
- 无名杀事件树或技能执行框架。

玩家可以自由移动任何有权限操作的桌面物件。系统不防止玩家误操作，也不为亲友局设计反作弊机制。

### 2.2 弱状态

除平台运行必需的信息外，不建立强制的游戏状态模型。

例如：

- 体力：移动武将牌遮挡体力牌，或翻转体力标记；
- 翻面：直接翻转武将牌；
- 横置：旋转武将牌 90°，或摆放横置标记；
- 阵亡：翻开身份牌、翻转武将牌或放置阵亡标记；
- 当前回合：手动传递回合标记；
- 装备：把装备牌摆放在武将牌旁边；
- 判定牌：摆入玩家判定区域；
- 技能附加牌：压在武将牌下方或摆放在旁边；
- 临时效果：通过通用 Token 或语音说明。

系统不需要理解这些摆放代表什么，也不要求玩家只能按照一种固定方式表达状态。

### 2.3 强同步

必须可靠同步以下桌面物件信息：

- 坐标；
- 旋转角度；
- 正面或背面；
- 堆叠顺序；
- 所属牌堆或容器；
- 是否位于私密手牌区；
- 玩家对物件的基础操作结果。

### 2.4 强可见性控制

必须正确维护：

- 玩家只能查看自己的手牌；
- 隐藏身份只对持有者可见；
- 卡牌移出私密区域后按桌面规则公开；
- 未入座观察者不能看到私密牌面；
- 不同浏览器会话中的可见性结果一致。

可见性权限是首版最重要的技术边界，比体力按钮或结算辅助更优先。

### 2.5 物件优先于界面按钮

能通过拖动、翻转、旋转或堆叠完成的操作，原则上不再增加专用按钮。

按钮和 Routine 只用于反复执行且明显降低操作负担的桌面动作，例如洗牌、初始发牌、自动整理布局和整桌重置。是否保留“摸一张”“摸两张”等快捷操作，要由多人试玩结果决定。

### 2.6 源码生成，不直接维护巨型 JSON

游戏数据、布局、Widget、Routine、素材和人数变体必须分离。TypeScript 源码生成 VirtualTabletop 兼容 JSON，再打包为 `.vtt`。最终的 `0.json` 是构建产物，不是主要维护源。

## 4. 首版支持范围

### 4.1 必须支持

- 4、5、6、7、8、9、10 人七种人数变体；
- 一个 `.vtt` 包内选择对应人数变体；
- 参数化座位和桌面布局生成器；
- 玩家区域以完整模块组织，可整体移动、锁定和重新排列；
- 自动整理布局，并保证玩家模块位于安全边界内且互不重叠；
- 宽松、标准紧凑和高密度三档布局；
- 私密手牌区；
- 隐藏身份牌；
- 武将牌；
- 体力牌或体力 Token；
- 主游戏牌堆；
- 弃牌区；
- 中央出牌和结算区；
- 装备区、判定区和附加牌区的视觉提示；
- 扩展包与备用物件收纳区；
- 通用回合、横置、阵亡、伤害类型和数字标记；
- 卡牌移动、翻转、旋转、堆叠、抽取和收纳；
- 洗牌、初始设置、布局整理和整桌重置；
- PC 浏览器优先，并保证平板和手机横屏可基本操作；
- `.vtt` 自动构建、验证和导入测试。

### 4.2 明确不支持

- 自动技能；
- 自动体力数字和加减按钮；
- 体力上限变量；
- `isChained`、`isTurnedOver`、`isDead` 等游戏状态变量；
- 当前行动玩家的强制状态；
- 目标声明和等待响应系统；
- 自动清理中央区；
- 自动判定身份配置是否合法；
- 自动规则日志或完整操作回放；
- 内置语音和视频；
- AI 玩家；
- 账号、匹配、排行、战绩和公共运营系统；
- 运行时无限新增座位或改变身份权限模型；
- 对 VirtualTabletop 核心源码的修改。

## 5. 桌面物件设计

### 5.1 玩家区域与玩家模块

每个玩家区域必须封装为一个完整玩家模块，至少包含：

- Seat；
- 私密手牌 Holder；
- 武将牌摆放位置；
- 身份牌摆放位置；
- 体力牌摆放位置；
- 装备区视觉提示或 Holder；
- 判定区视觉提示或 Holder；
- 附加牌或标记自由摆放空间；
- 玩家编号或名称标签。

玩家模块必须满足：

- 模块可以整体拖动，内部组件始终跟随；
- 布局调整完成后可以整体锁定，防止游戏中误拖；
- 支持紧凑与展开两种显示密度；
- 标签和关键文字不得悬出模块边界；
- 自动布局以模块完整边界框为单位，不能只按中心坐标排列；
- 玩家模块移动不得改变 Seat、手牌归属或私密可见性；
- 允许房主在自动整理后进行少量手动微调。

这些区域以背景线框、标签或轻量底板提示为主，不强制检测卡牌是否放入正确区域。模块化的目的主要是改善屏幕适配、越界和重叠问题，不是实现动态人数系统。

### 5.2 公共区域

桌面中心至少包含：

- 主牌堆；
- 弃牌区；
- 中央出牌与结算区；
- 武将牌堆或武将选择区；
- 身份牌堆；
- 通用标记供应区。

公共区域位置原则上固定，并定义不可被玩家模块覆盖的中央保留区。

### 5.3 桌外收纳区

用于放置：

- 扩展牌包；
- 备用武将；
- 备用身份；
- 体力牌和 Token；
- 规则说明；
- 不参与当前游戏的内容。

收纳区可以通过 Deck、Pile、Holder 或容器类 Widget 实现，避免备用内容挤占主桌面。

## 6. 4–10 人自适应模块化布局策略

### 6.1 统一生成器

不得手工维护七套彼此独立的布局 JSON。布局由参数生成：

```ts
createTableVariant({ playerCount: 4 });
createTableVariant({ playerCount: 5 });
// ...
createTableVariant({ playerCount: 10 });
```

各人数变体仍保留固定 Seat 和私密权限，但全部共用同一玩家模块、边界检测和自动整理算法。

### 6.2 安全边界与中央保留区

布局生成器必须显式定义：

- 桌布或可用画布边界；
- 四周安全边距；
- 中央公共区域保留边界；
- 玩家模块之间的最小间距；
- 模块可用的旋转方向和完整边界框。

任何玩家模块的完整边界不得超出安全区域，也不得遮挡主牌堆、弃牌区或中央结算区。安全边距应作为配置项，不在多个文件中硬编码。

### 6.3 三档密度

- 4–6 人：宽松布局，玩家区域显示完整标签和较宽手牌区；
- 7–8 人：标准紧凑布局，减少装饰和模块间距；
- 9–10 人：高密度布局，优先采用矩形周边排列或上下分排，不通过无限扩大圆环解决拥挤。

密度切换可以调整模块尺寸、标签尺寸、手牌堆叠偏移和区域间距，但不得修改玩家的 Seat、权限和私密信息。

### 6.4 防重叠排列

自动布局必须以玩家模块的实际宽高或预先定义的边界框计算位置，并满足：

- 相邻模块之间保留最小间距；
- 玩家模块不得与中央保留区相交；
- 标签、手牌区和状态区必须计入边界；
- 手牌区在手牌数量增加时动态减小堆叠间距；
- 无法容纳时优先切换紧凑模式或矩形排列，而不是将组件推到桌布外。

### 6.5 自动整理、解锁与锁定

每个变体应提供克制的布局辅助：

- `自动整理`：按当前人数和密度重新计算玩家模块位置；
- `解锁布局`：允许房主或有权限玩家整体拖动玩家模块；
- `锁定布局`：固定玩家模块，避免游戏中误拖。

自动整理只改变玩家模块的位置、旋转和显示密度，不移动玩家手牌、武将、装备等已归属模块内部的游戏物件，也不改变任何规则状态。

### 6.6 代表布局优先验证

先完成：

- 4 人：最宽松边界；
- 8 人：常见多人边界；
- 10 人：最拥挤边界。

三种代表布局通过后再生成 5、6、7、9 人变体。

### 6.7 固定俯视桌面优先

首版优先采用所有玩家看到同一张固定俯视桌面的方案，不强求本地玩家始终位于屏幕下方。只有确认 VirtualTabletop 能稳定支持座位相对视角后，才将其列入后续优化。

## 8. 构建流程

```text
只读参考数据
    ↓
项目内标准化 TypeScript 数据
    ↓
生成桌面物件、玩家模块和 4–10 人布局
    ↓
应用安全边界、防重叠和密度策略
    ↓
生成 VirtualTabletop 兼容 JSON 变体
    ↓
校验 ID、引用、权限、坐标、重叠和素材路径
    ↓

    ↓
压缩为 .vtt
    ↓
导入本地 VirtualTabletop
    ↓
多浏览器人工验收
```

阶段完成前必须运行：

```powershell
pnpm build
pnpm validate
pnpm test
pnpm check
```

## 9. 阶段计划

## P0：最小虚拟桌面技术验证

### 目标

证明项目可以生成并导入 `.vtt`，并验证私密信息、物件同步和实体状态表达。

### 实施内容

1. 只读分析 VirtualTabletop 的 `.vtt` 格式和最小游戏包示例。
2. 定义最小 TypeScript Widget 类型和唯一 ID 生成规则。
3. 实现基础 JSON 生成器和 `.vtt` 打包脚本。
4. 制作四人占位测试桌面：
   - 四个座位；
   - 四个私密手牌区；
   - 隐藏身份占位牌；
   - 一副占位主牌堆；
   - 武将占位牌；
   - 体力占位牌；
   - 弃牌区；
   - 中央处理区。
5. 验证以下实体操作：
   - 抽牌；
   - 从手牌移出卡牌；
   - 翻牌；
   - 旋转武将牌；
   - 移动武将牌遮挡体力；
   - 牌的堆叠与拆分；
   - 多会话实时同步。
6. 不实现体力变量、状态变量或规则按钮。

### 交付物

- `dist/Sanguosha-Manual-P0.vtt`；
- 最小构建与验证脚本；
- P0 测试报告；
- 私密手牌和身份可见性截图；
- VirtualTabletop 关键属性说明。

### 验收标准

- `.vtt` 可正常导入；
- 玩家只能看到自己的手牌和身份；
- 观察者或其他座位不能看到私密牌面；
- 移动、翻转、旋转和堆叠在多浏览器中同步；
- 刷新或重新进入后桌面状态可恢复；
- Widget ID、素材路径和 JSON 结构校验通过；
- 两个上游仓库无修改。

### 停止条件

P0 未通过前，不导入正式三国杀牌堆、武将和真实素材。

## P1：4–10 人自适应模块化布局

### 目标

建立统一玩家模块和自适应布局生成器，在七个人数变体中解决越界、重叠和不同屏幕比例下的可操作性问题。

### 实施内容

1. 建立统一玩家模块，内部包含 Seat、私密手牌、武将、身份、体力、装备、判定和附加牌区域。
2. 建立公共牌堆、弃牌区、中央处理区、中央保留区和桌外收纳区。
3. 定义桌布边界、四周安全边距、模块间最小间距和模块边界框。
4. 实现宽松、标准紧凑和高密度三档布局。
5. 先完成 4、8、10 人代表布局，再自动生成 5、6、7、9 人布局。
6. 高密度布局优先采用矩形周边排列、上下分排或模块紧凑化，不允许通过坐标越界容纳更多玩家。
7. 实现自动整理、解锁布局和锁定布局；自动整理不得改变 Seat、权限或模块内部游戏状态。
8. 手牌区根据容纳数量动态压缩堆叠间距，常见手牌数量不得明显溢出模块。
9. 编写坐标越界、模块重叠、中央区侵占、最小点击尺寸、Seat 数量和权限稳定性测试。
10. 为每个人数生成截图或结构快照，并记录所用密度策略。

### 交付物

- 可移动、可锁定的玩家模块；
- 4–10 人自适应布局生成器；
- 七个人数变体；
- 自动整理与布局锁定 Routine；
- 布局边界、重叠和中央保留区自动测试；
- 4、8、10 人代表布局截图；
- 布局设计说明。

### 验收标准

- 七个变体均可独立加载；
- 所有玩家模块完整位于安全边界内；
- 4、8、10 人桌面无玩家模块重叠或中央公共区侵占；
- 中间人数由同一生成器稳定生成；
- 自动整理可重复执行且结果稳定；
- 解锁后玩家模块可整体拖动，锁定后不会被普通游戏操作误移；
- 移动或整理玩家模块不改变手牌归属、身份可见性和 Seat 绑定；
- 主牌堆、弃牌区和中央处理区易于访问；
- 10 人局在常见 PC 分辨率下仍可辨认和拖动；
- 修改玩家模块时无需修改七套 JSON。

## P2：桌面物件与状态表达组件

### 目标

完成不依赖抽象变量的三国杀桌面物件系统。

### 实施内容

1. 设计体力牌或双面体力 Token。
2. 设计武将牌、身份牌和通用卡牌模板。
3. 设计回合、横置、阵亡、火焰、雷电和数字 Token。
4. 为装备区、判定区和附加牌区添加视觉提示。
5. 设计桌外扩展包和备用组件收纳方式。
6. 验证遮挡、翻转、旋转和层级关系。
7. 编写一页式桌面操作说明。

### 交付物

- 通用桌面物件生成器；
- 体力、身份、武将和 Token 占位组件；
- 玩家区域视觉提示；
- 桌外收纳组件；
- 实体状态表达说明。

### 验收标准

- 玩家可通过移动武将牌表达体力；
- 可通过翻转或旋转表达翻面、横置和阵亡；
- 装备牌、判定牌和附加牌可以自由摆放；
- 不依赖体力、横置、翻面或阵亡变量；
- Token 不强制触发任何规则逻辑。

## P3：身份、牌堆、武将和数据管线

### 目标

建立可追踪、可校验的三国杀内容数据，并导入首批可试玩内容。

### 实施内容

1. 只读分析 Noname 中经过白名单批准的数据：
   - 基础牌堆；
   - 卡牌名称、类别、花色和点数；
   - 身份模式配置；
   - 武将名称与技能说明文字；
   - 中文术语。
2. 编写受控提取器，不读取或迁移技能执行代码。
3. 将数据转换为项目内标准格式，不在运行时依赖 Noname。
4. 建立卡牌数量、花色、点数、唯一 ID 和素材引用校验。
5. 建立 4–10 人默认身份牌预设，并允许房主手动更换身份牌组成。
6. 导入首批身份牌、基础游戏牌和武将牌。
7. 所有图片和字体必须记录来源与授权状态。

### 交付物

- 标准化卡牌数据；
- 标准化身份与武将数据；
- 数据提取器；
- 来源和许可证清单；
- 数据校验测试。

### 验收标准

- 数据来源可追踪；
- 身份牌和手牌可见性正确；
- 牌堆数量、花色和点数通过人工与自动校验；
- 武将技能仅显示文字，不执行逻辑；
- 没有迁移任何事件树、技能脚本或 AI；
- 未确认授权的素材不进入公开发布包。

## P4：最少量便利操作

### 目标

只为明显重复且容易出错的桌面动作提供便利，不增加规则约束。

### 候选功能

- 洗主牌堆；
- 随机发隐藏身份；
- 发初始手牌；
- 自动整理玩家模块；
- 解锁和锁定布局；
- 收集并重置主牌堆；
- 整桌重置；
- 经试玩确认后可选增加摸一张、摸两张。

### 实施原则

1. 每个 Routine 只移动或处理桌面物件。
2. Routine 不判断回合、技能、距离或合法性。
3. 玩家始终可以绕过快捷操作，直接手动拖动卡牌。
4. 自动整理只处理玩家模块的布局属性，不处理任何三国杀规则状态。
5. 自动重置前需要明显确认，避免误清空亲友局。
6. 未通过试玩证明有价值的按钮不加入首版。

### 交付物

- 最小 Routine 集；
- Routine 行为说明；
- 布局整理与重置安全验证；
- 多浏览器同步测试。

### 验收标准

- 洗牌和发牌不泄露私密信息；
- Routine 不改变规则状态；
- 自动整理不改变 Seat、手牌归属或身份可见性；
- 手动操作始终可替代快捷操作；
- 重置不会遗留卡牌或重复生成物件；
- 按钮数量保持克制。

## P5：视觉、移动端和多人稳定性

### 目标

形成适合长期好友局使用的稳定版本。

### 实施内容

1. 统一桌面、卡牌、区域、玩家模块和 Token 的视觉语言。
2. 优化卡牌尺寸、文字可读性、拖动手感和堆叠层级。
3. 优化 4–10 人三档密度、自适应边界和防重叠布局。
4. 在常见 PC 分辨率和浏览器缩放下验证自动整理结果。
5. 重点测试 PC；补充平板和手机横屏基本操作。
6. 测试断线重进、刷新、换座、观察者加入、模块移动和多人同步。
7. 检查私密信息泄漏，确认模块移动不影响权限。
8. 优化 `.vtt` 包体积和素材加载。
9. 编写玩家使用说明、房主说明和已知限制。

### 交付物

- `dist/Sanguosha-Manual-Tabletop.vtt`；
- 4–10 人截图矩阵；
- 不同分辨率和布局密度测试截图；
- 多人测试报告；
- 使用说明；
- 素材来源和许可证清单；
- 已知问题清单。

### 验收标准

- 七个人数变体全部可加载；
- 4、8、10 人完成完整多人试玩；
- 自动整理后不存在已知严重越界、重叠或中央区遮挡；
- 私密手牌和身份无已知严重泄漏；
- 玩家模块移动、锁定和重新整理在多人客户端中同步一致；
- 断线重进后桌面状态可继续使用；
- PC 端体验稳定；
- 平板和手机横屏可完成基础操作；
- 无自动规则引擎或隐藏的强制状态系统。

## 10. 测试矩阵

### 10.1 自动测试

必须覆盖：

- `.vtt` 包结构；
- JSON 可解析性；
- Widget ID 唯一性；
- Widget 引用完整性；
- 素材路径有效性；
- 4–10 人 Seat 数量；
- 私密 Holder 配置；
- 玩家模块完整性和父子引用；
- 布局坐标边界；
- 玩家模块之间的重叠；
- 玩家模块与中央保留区的相交；
- 不同密度模式下的安全边距；
- 自动整理的确定性和幂等性；
- 布局移动前后 Seat、手牌归属和身份权限不变；
- 数据数量与唯一 ID；
- 七个变体可重复生成；
- 构建结果可重复。

### 10.2 人工浏览器测试

至少验证：

- 两个不同玩家互相不可见手牌；
- 身份牌只对本人可见；
- 观察者不可见私密牌面；
- 从手牌出牌后牌面正确公开；
- 翻转和旋转实时同步；
- 遮挡体力牌在不同客户端显示一致；
- 牌堆抽取和洗牌结果同步；
- 玩家模块可整体移动、锁定和重新整理；
- 自动整理不会改变玩家的手牌、身份和 Seat；
- 玩家断线重进；
- 10 人布局无明显越界、重叠或中央区遮挡。

### 10.3 试玩测试

每次试玩重点记录：

- 哪些按钮实际有用；
- 哪些按钮可以删除；
- 哪些区域太小或太远；
- 玩家模块是否需要手动微调；
- 自动整理是否产生不自然的间距或朝向；
- 哪些人数需要切换更紧凑的密度；
- 牌堆是否容易误取；
- 体力牌是否容易遮挡和调整；
- 手牌区在大量手牌时是否溢出；
- Token 是否足够；
- 4–10 人布局是否需要独立密度调整；
- 是否出现私密信息泄漏。

## 11. 素材与许可证原则

1. 项目代码使用仓库确认的许可证。
2. 参考项目的代码许可证不自动覆盖图片、字体、声音和卡面素材。
3. 每个正式素材必须记录：
   - 来源；
   - 作者或权利人；
   - 许可证或授权说明；
   - 是否允许修改；
   - 是否允许再分发。
4. 未确认授权的素材只能保留在本地私人测试环境，不进入公开发行包。
5. 不直接复制 Tabletop Simulator 模组中的远程卡面、模型或对象数据。
6. 不将 Noname 的素材默认视为可自由再分发。
7. 首版开发可以优先使用自制占位素材，功能通过后再替换。

## 12. Git 与阶段管理

建议版本：

```text
v0.1  P0 最小虚拟桌面验证
v0.2  P1 自适应模块化布局
v0.3  P2 桌面物件组件
v0.4  P3 身份、牌堆和武将数据
v0.5  P4 最少量便利操作
v1.0  P5 好友局稳定版
```

每个阶段：

1. 使用独立分支；
2. 保持提交范围单一；
3. 提交源码、测试和文档；
4. 构建产物是否入库由 `.gitignore` 和发布方式决定；
5. 阶段验收通过后再进入下一阶段；
6. 不在一个阶段中顺带实现后续规则功能。

## 13. Codex 执行边界

Codex 在任何阶段都必须：

- 先阅读 `AGENTS.md` 和本计划；
- 将 `../noname-main`、`../virtualtabletop` 和本地 Tabletop Simulator 参考目录视为只读；
- 只在本项目目录写入新代码；
- 使用 pnpm；
- 保持 TypeScript 数据、布局、Widget 和 Routine 分离；
- 不执行来源不明的 Lua 或脚本；
- 不下载参考模组的远程卡面；
- 不引入自动规则引擎；
- 不为了“完整”而擅自增加体力、横置、阵亡或回合变量；
- 不把模块化布局扩大为运行时无限新增玩家或修改私密权限模型；
- 每阶段完成后输出改动文件、测试结果、构建结果和已知问题。

## 14. 当前已冻结决策

以下决定在实施中不得自行改变：

1. 支持 4–10 人；
2. 七个人数变体由统一生成器产生；
3. 项目定位为联网虚拟桌面，而非三国杀规则程序；
4. 采用“弱规则、弱状态、强同步、强可见性控制”；
5. 体力、翻面、横置、阵亡等优先由实体物件表达；
6. 不设计反作弊机制；
7. 外部语音沟通；
8. Noname 只作为内容参考；
9. Tabletop Simulator 模组只作为布局参考；
10. VirtualTabletop 上游源码原则上不修改；
11. 正式功能按 P0–P5 逐阶段验收；
12. P0 只使用占位内容，不提前实现正式牌堆和规则；
13. 玩家区采用可移动、可锁定的完整模块，主要用于解决越界、重叠和屏幕适配问题；
14. 模块化布局不等于动态人数系统，首版仍采用 4–10 人固定 Seat 与权限变体；
15. 自动整理不得改变 Seat、手牌归属、身份可见性或任何三国杀规则状态。

## 15. v1.0 完成定义

只有同时满足以下条件，项目才可标记为 v1.0：

- 一个 `.vtt` 包包含 4–10 人七个可用变体；
- 私密手牌和隐藏身份通过多人验证；
- 卡牌移动、翻转、旋转、堆叠和牌堆操作稳定同步；
- 玩家可通过实体物件完成体力、翻面、横置、阵亡和标记表达；
- 玩家模块可以整体移动、锁定并自动整理；
- 七个变体在安全边界内无已知严重重叠或中央区遮挡；
- 4、8、10 人分别完成至少一局完整多人试玩；
- 不存在已知严重私密信息泄漏；
- 构建、校验和测试全部通过；
- 正式素材具有可追踪的来源与授权记录；
- 使用说明和已知限制完整；
- 项目中不存在自动技能、自动伤害、自动距离、自动响应或自动胜负判断。
